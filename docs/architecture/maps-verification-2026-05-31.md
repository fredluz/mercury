# Mercury Architecture Maps Verification - 2026-05-31

This verifies `docs/architecture/code-map.md` and `docs/architecture/architecture-map.md` against the current code tree. I checked entry points, Electron main/preload/renderer boundaries, CLI adapters, IPC registration, runtime verification, BFF clients, connection modes, and the Hermes chat/session/cron paths.

## 1. Claims Confirmed

- **Top-level package/build layout is accurate.** `package.json` points Electron main at `./out/main/index.js` and the CLI bin at `./out/cli/index.js` (`package.json:5`, `package.json:6`-`package.json:8`). The scripts match the map: `typecheck` runs node/web/cli typechecks, `build:cli` emits `out/cli/index.js` and chmods it, and `build` runs typecheck, CLI build, then `electron-vite build` (`package.json:17`-`package.json:20`, `package.json:33`-`package.json:34`).

- **Electron main startup flow is substantially correct.** `src/main/index.ts` creates the `BrowserWindow` with `../preload/index.js`, loads dev URL or `../renderer/index.html`, builds the menu, registers IPC handlers, creates the window, sets up updater handlers, and auto-starts SSH support when configured (`src/main/index.ts:93`-`src/main/index.ts:109`, `src/main/index.ts:161`-`src/main/index.ts:168`, `src/main/index.ts:353`-`src/main/index.ts:387`). Shutdown stops gateways, SSH tunnel, health polling, and active chat (`src/main/index.ts:394`-`src/main/index.ts:407`).

- **IPC composition root matches the map.** `registerIpcHandlers` registers install, config, chat, trace, gateway, sessions, knowledge, models, cron, and system IPC modules, and re-exports `abortActiveChat` (`src/main/ipc/index.ts:1`-`src/main/ipc/index.ts:26`).

- **Preload composition and contract are real.** `src/preload/index.ts` exposes both `electron` and `hermesAPI` via `contextBridge` (`src/preload/index.ts:5`-`src/preload/index.ts:16`). `src/preload/api/index.ts` composes install/config/chat/navigation/knowledge/models/app fragments into `hermesAPI` (`src/preload/api/index.ts:1`-`src/preload/api/index.ts:17`). The d.ts declares both `Window.electron` and `Window.hermesAPI` (`src/preload/index.d.ts:579`-`src/preload/index.d.ts:583`).

- **Renderer entry/routing claims are accurate.** `main.tsx` renders `App` under `I18nProvider` (`src/renderer/src/main.tsx:11`-`src/renderer/src/main.tsx:17`). `App.tsx` owns splash/welcome/install/setup/main routing and runs connection/install checks (`src/renderer/src/App.tsx:12`, `src/renderer/src/App.tsx:24`-`src/renderer/src/App.tsx:99`, `src/renderer/src/App.tsx:134`-`src/renderer/src/App.tsx:157`). `Layout.tsx` owns active view, active profile, session state, remote-only gating, runtime diagnostics, updater events, and menu events (`src/renderer/src/screens/Layout/Layout.tsx:102`-`src/renderer/src/screens/Layout/Layout.tsx:136`, `src/renderer/src/screens/Layout/Layout.tsx:202`-`src/renderer/src/screens/Layout/Layout.tsx:212`, `src/renderer/src/screens/Layout/Layout.tsx:228`-`src/renderer/src/screens/Layout/Layout.tsx:256`, `src/renderer/src/screens/Layout/Layout.tsx:342`-`src/renderer/src/screens/Layout/Layout.tsx:354`).

- **Renderer-to-main chat path is correct.** Preload invokes `"send-message"` and exposes listener cleanup functions for chat events (`src/preload/api/chat.ts:8`-`src/preload/api/chat.ts:14`, `src/preload/api/chat.ts:40`-`src/preload/api/chat.ts:105`). Main `chat.ts` handles `"send-message"`, calls `runChatMessage`, and fans out `chat-chunk`, `chat-done`, `chat-error`, `chat-trace-event`, `chat-tool-progress`, and `chat-usage` (`src/main/ipc/chat.ts:61`-`src/main/ipc/chat.ts:121`).

- **Chat service is the shared desktop/CLI orchestration seam.** `registerChatIpc` explicitly delegates chat orchestration to `services/chat-service.ts` (`src/main/ipc/chat.ts:61`-`src/main/ipc/chat.ts:64`). CLI `chat send` dynamically imports `../main/services/chat-service` and calls `runChatMessage` with callbacks for text/JSON/NDJSON output and SIGINT abort (`src/cli/chat-commands.ts:194`-`src/cli/chat-commands.ts:228`, `src/cli/chat-commands.ts:233`-`src/cli/chat-commands.ts:258`).

- **Chat service behavior in the architecture map is mostly accurate.** It aborts the previous active run (`src/main/services/chat-service.ts:194`-`src/main/services/chat-service.ts:202`), creates a Mercury trace run (`src/main/services/chat-service.ts:207`-`src/main/services/chat-service.ts:210`), prepares the backend (`src/main/services/chat-service.ts:460`-`src/main/services/chat-service.ts:462`), dispatches to Hermes (`src/main/services/chat-service.ts:478`-`src/main/services/chat-service.ts:485`), records trace events/usage (`src/main/services/chat-service.ts:317`-`src/main/services/chat-service.ts:457`), and updates session cache/profile/title metadata best-effort (`src/main/services/chat-service.ts:367`-`src/main/services/chat-service.ts:380`, `src/main/services/chat-service.ts:536`-`src/main/services/chat-service.ts:560`).

- **Hermes runtime/BFF split exists and is central.** The runtime barrel exports `ProfileRuntimeManager` and the singleton `profileRuntimeManager` (`src/main/hermes/runtime.ts:1`-`src/main/hermes/runtime.ts:9`). `manager.ts` normalizes profile/mode, branches local/SSH/remote, and rejects pure remote profile-bound execution with `runtime-unsupported-remote-profile` (`src/main/hermes/runtime/manager.ts:152`-`src/main/hermes/runtime/manager.ts:185`). `api-runtime.ts` asserts verified API/SSH handles, exact profile match, valid auth, and required capabilities (`src/main/hermes/runtime/api-runtime.ts:12`-`src/main/hermes/runtime/api-runtime.ts:67`).

- **Local runtime verification is fail-closed and profile-bound.** Local resolution refuses stale state, unmanaged process evidence, not-ready managed gateways, port conflicts, profile mismatches, invalid API keys, and missing capabilities (`src/main/hermes/runtime/local-runtime.ts:60`-`src/main/hermes/runtime/local-runtime.ts:230`, `src/main/hermes/runtime/local-runtime.ts:233`-`src/main/hermes/runtime/local-runtime.ts:289`). Local gateway start writes API host/port/key env, tracks managed process/PID/command evidence, and records unverified identity until API readiness is proven (`src/main/hermes/runtime/manager.ts:194`-`src/main/hermes/runtime/manager.ts:279`).

- **SSH runtime verification is real.** SSH mode gets the tunnel URL, verifies remote runtime identity via `sshVerifyProfileRuntime`, rejects unverified evidence, probes capabilities through the tunnel, and returns a `ssh-api` handle with auth headers (`src/main/hermes/runtime/ssh-runtime.ts:17`-`src/main/hermes/runtime/ssh-runtime.ts:105`).

- **Pure remote HTTP fail-closed claim is correct for profile-bound execution.** `resolveRuntime` creates an unverified external identity and throws `runtime-unsupported-remote-profile` for `mode === "remote"` (`src/main/hermes/runtime/manager.ts:173`-`src/main/hermes/runtime/manager.ts:183`). CLI maps that runtime code to unsupported exit behavior (`src/cli/errors.ts:75`).

- **Hermes BFF clients are built only from verified runtime handles.** `profileHermesBffClientForRuntime` calls `assertVerifiedApiRuntimeHandle` before constructing `ProfileHermesBffClient` (`src/main/hermes/bff/client.ts:513`-`src/main/hermes/bff/client.ts:520`). The client applies runtime auth headers and strips reserved caller-provided headers such as `authorization`, `x-mercury-request-id`, `accept`, and `content-type` (`src/main/hermes/bff/client.ts:381`-`src/main/hermes/bff/client.ts:393`, `src/main/hermes/bff/client.ts:553`-`src/main/hermes/bff/client.ts:568`).

- **Chat uses the Hermes runs API/BFF, not legacy chat-completions.** `sendMessage` asserts a verified runtime then calls `sendMessageViaApi` (`src/main/hermes/gateway.ts:20`-`src/main/hermes/gateway.ts:39`). `sendMessageViaApi` delegates to `sendMessageViaRunsApi` (`src/main/hermes/chat-api.ts:8`-`src/main/hermes/chat-api.ts:18`). Runs API submits to `/v1/runs`, streams `/v1/runs/:id/events`, stops `/v1/runs/:id/stop`, and resolves approvals through `/v1/runs/:id/approval` (`src/main/hermes/bff/runs.ts:43`-`src/main/hermes/bff/runs.ts:148`). The old probe explicitly says legacy chat-completions are no longer used (`src/main/hermes/chat-api.ts:26`-`src/main/hermes/chat-api.ts:31`).

- **Session creation/read before chat is a real part of the chat path.** `runChatMessage` creates or reads a Hermes session via a verified runtime before `sendMessage`, projects the server session into the Mercury cache, then passes the durable session id into the run submission (`src/main/services/chat-service.ts:460`-`src/main/services/chat-service.ts:485`). The BFF sessions client uses `/api/sessions` and `/api/sessions/:id` (`src/main/hermes/bff/sessions.ts:20`-`src/main/hermes/bff/sessions.ts:40`).

- **Connection mode helpers match the maps.** `isRemoteMode` is true for both `remote` and `ssh`, while `isRemoteOnlyMode` is true only for pure remote HTTP (`src/main/hermes/connection.ts:79`-`src/main/hermes/connection.ts:87`). Remote startup tests only `/health` with optional bearer token (`src/main/hermes/connection.ts:382`-`src/main/hermes/connection.ts:405`).

- **Mercury-owned data claims are confirmed.** Connection config is stored in `<HERMES_HOME>/desktop.json` (`src/main/config.ts:24`-`src/main/config.ts:45`, `src/main/config.ts:47`-`src/main/config.ts:74`). - **Cron/job BFF routing is present.** `cronjobs.ts` switches to a verified BFF jobs client in remote/SSH modes (`src/main/cronjobs.ts:130`-`src/main/cronjobs.ts:140`, `src/main/cronjobs.ts:215`-`src/main/cronjobs.ts:235`, `src/main/cronjobs.ts:580`-`src/main/cronjobs.ts:611`, `src/main/cronjobs.ts:626`-`src/main/cronjobs.ts:704`). ## 2. Discrepancies

- **Map says renderer "calls `window.hermesAPI` only"; code also uses `window.electron`.** This is not a main-process import violation, but the absolute wording is false. `App.tsx` reads `window.electron?.process?.platform` to decide the macOS drag region (`src/renderer/src/App.tsx:22`, `src/renderer/src/App.tsx:160`-`src/renderer/src/App.tsx:166`), and preload explicitly exposes `electron` beside `hermesAPI` (`src/preload/index.ts:5`-`src/preload/index.ts:16`; `src/preload/index.d.ts:579`-`src/preload/index.d.ts:583`).

- **Map's startup flow omits the separate main-process SSH auto-start and implies the renderer is the only startup SSH path.** Renderer startup calls `window.hermesAPI.startSshTunnel()` and then enters main (`src/renderer/src/App.tsx:31`-`src/renderer/src/App.tsx:43`), but main also auto-starts the remote gateway, tunnel, and remote API key on app ready if SSH is already configured (`src/main/index.ts:374`-`src/main/index.ts:387`). This duplicate startup path matters for debugging SSH races and key caching.

- **Map says BFF clients "accept no arbitrary renderer-controlled paths or tokens"; code enforces token/header safety but not by route allowlisting in the generic client.** The generic `ProfileHermesBffClient` accepts a `path` string from its internal callers and concatenates it into the URL (`src/main/hermes/bff/client.ts:376`-`src/main/hermes/bff/client.ts:379`). It does strip reserved headers and inject runtime auth (`src/main/hermes/bff/client.ts:381`-`src/main/hermes/bff/client.ts:393`, `src/main/hermes/bff/client.ts:553`-`src/main/hermes/bff/client.ts:568`). The practical safety boundary is that renderer never receives this client and typed family clients provide fixed paths, but the map overstates what `client.ts` itself enforces.

- **Map says main IPC owns "argument validation" as a durable boundary; validation is uneven.** Chat title and approval requests validate shapes (`src/main/ipc/chat.ts:123`-`src/main/ipc/chat.ts:161`), but many config/system/cron handlers forward primitive arguments directly to services (`src/main/ipc/config.ts:35`-`src/main/ipc/config.ts:124`, `src/main/ipc/system.ts:41`-`src/main/ipc/system.ts:69`, `src/main/ipc/cron.ts:20`-`src/main/ipc/cron.ts:62`). The "argument validation" claim should be treated as an aspiration, not a consistent current invariant.

- **Map's "IPC files should stay thin" is mostly true, but not absolute.** `chat.ts` includes notification policy and best-effort notification dispatch after completion/failure (`src/main/ipc/chat.ts:93`-`src/main/ipc/chat.ts:118`), and it performs approval request validation locally (`src/main/ipc/chat.ts:135`-`src/main/ipc/chat.ts:161`). This is reasonable adapter behavior, but it is more than pure channel registration.

- **Map under-describes chat persistence: it says dispatch to Hermes API/BFF, but code first creates or reads a Hermes session resource.** This is not just session metadata after the fact. `runChatMessage` calls `createHermesSession` or `readHermesSession`, projects it into the session cache, records a `session.created` trace, and only then calls `sendMessage` with the session id (`src/main/services/chat-service.ts:460`-`src/main/services/chat-service.ts:485`). This is load-bearing for durable chat/session bugs.

- **Map says `src/main/services/cron-service.ts` owns remote/local routing; actual remote/local routing lives mostly in `src/main/cronjobs.ts`.** `cron-service.ts` is a thin wrapper that delegates to `../cronjobs` and marks runtimes stale (`src/main/services/cron-service.ts:1`-`src/main/services/cron-service.ts:18`, `src/main/services/cron-service.ts:20`-`src/main/services/cron-service.ts:78`). The real remote/BFF branching is in `src/main/cronjobs.ts` (`src/main/cronjobs.ts:215`-`src/main/cronjobs.ts:235`, `src/main/cronjobs.ts:580`-`src/main/cronjobs.ts:704`).

- **Map says pure remote HTTP startup tests remote `/health`; true, but it can still enter the main UI even though profile-bound execution later fails closed.** `App.tsx` moves to `main` when `testRemoteConnection` returns true (`src/renderer/src/App.tsx:44`-`src/renderer/src/App.tsx:54`), while runtime resolution later throws for pure remote profile-bound work (`src/main/hermes/runtime/manager.ts:173`-`src/main/hermes/runtime/manager.ts:183`). The map states both facts separately, but should explicitly call out the UX consequence: startup success does not mean chat/cron/profile execution will work in pure remote mode.

- **Map's "Hermes-owned data" row lists `config.ts`, which is ambiguous.** `src/main/config.ts` is Mercury code that owns both Mercury desktop connection config (`desktop.json`) and low-level reads/writes into Hermes profile `.env` and `config.yaml` (`src/main/config.ts:24`-`src/main/config.ts:74`, `src/main/config.ts:100`-`src/main/config.ts:177`, `src/main/config.ts:210`-`src/main/config.ts:238`). Saying "config lives in Hermes profile storage" is only true for profile env/config, not for desktop connection state.

## 3. Important Things the Maps OMIT

- **Electron security-relevant `BrowserWindow` settings are omitted.** The main window runs with `sandbox: false` and `webviewTag: true` (`src/main/index.ts:105`-`src/main/index.ts:109`). Any boundary/security work should know this before assuming a narrow preload-only renderer sandbox.

- **The maps omit the API key generation/caching path for local and SSH runtimes.** Local runtime auto-generates and persists `API_SERVER_KEY` when missing (`src/main/hermes/runtime/manager.ts:569`-`src/main/hermes/runtime/manager.ts:577`) and passes it to the gateway environment (`src/main/hermes/runtime/manager.ts:229`-`src/main/hermes/runtime/manager.ts:233`). SSH keys are cached per normalized profile after reading the remote `.env` (`src/main/hermes/connection.ts:89`-`src/main/hermes/connection.ts:107`; `src/main/services/config-service.ts:229`-`src/main/services/config-service.ts:240`). This is central to Hermes connection failures.

- **The maps omit capability gating details.** Mercury requires `run_submission` and `session_resources`, treats `run_events_sse`, `run_stop`, and `run_approval_response` as optional summaries, and maps invalid API key/missing feature/network/malformed capability responses into runtime identity state (`src/main/hermes/connection.ts:144`-`src/main/hermes/connection.ts:149`, `src/main/hermes/connection.ts:236`-`src/main/hermes/connection.ts:328`; `src/main/hermes/runtime/api-runtime.ts:44`-`src/main/hermes/runtime/api-runtime.ts:66`).

- **The maps omit local port assignment and conflict rules.** Default profile uses port `8642`; named profiles get stable hashed ports; named profiles cannot use the default port, and two live profiles cannot share a local API port (`src/main/hermes/connection.ts:13`-`src/main/hermes/connection.ts:33`, `src/main/hermes/runtime/local-runtime.ts:233`-`src/main/hermes/runtime/local-runtime.ts:289`). This is crucial for multi-profile runtime bugs.

- **The maps omit stale runtime invalidation triggers.** Env/model/config/connection/SSH changes mark profile or all runtimes stale and sometimes restart/revalidate gateways (`src/main/services/config-service.ts:72`-`src/main/services/config-service.ts:95`, `src/main/services/config-service.ts:105`-`src/main/services/config-service.ts:118`, `src/main/services/config-service.ts:135`-`src/main/services/config-service.ts:166`, `src/main/services/config-service.ts:179`-`src/main/services/config-service.ts:209`). Cron mutations also mark runtime stale (`src/main/services/cron-service.ts:16`-`src/main/services/cron-service.ts:18`).

- **The maps omit BFF diagnostics.** Every BFF request records profile, transport, API base URL, auth fingerprint, status, duration, retry count, and run/session/job IDs (`src/main/hermes/bff/client.ts:474`-`src/main/hermes/bff/client.ts:510`). This is important for verifying Hermes connection behavior without guessing.

- **The maps omit the Hermes run concurrency/abort registry path.** Runs are scheduled through `hermesRunRegistry`, and abort destroys the active HTTP request and posts run stop when a run ID exists (`src/main/hermes/runs-api.ts:72`-`src/main/hermes/runs-api.ts:117`). Chat service has its own active run token and abort finalization (`src/main/services/chat-service.ts:92`-`src/main/services/chat-service.ts:144`, `src/main/services/chat-service.ts:487`-`src/main/services/chat-service.ts:497`).

- **The maps omit session cache internals that matter to performance and profile correctness.** Cache is keyed by session/profile, deduped, syncs from SQLite scopes, and writes to `<HERMES_HOME>/desktop/sessions.json` (`src/main/session-cache.ts:17`-`src/main/session-cache.ts:19`, `src/main/session-cache.ts:81`-`src/main/session-cache.ts:111`, `src/main/session-cache.ts:216`-`src/main/session-cache.ts:259`). This matters because the UI can show cached sessions even when Hermes session reads differ.

- **The maps omit trace-store limits and redaction.** Trace storage caps runs and agent delta events and redacts secret-looking keys/text (`src/main/trace-store.ts:24`-`src/main/trace-store.ts:33`, `src/main/trace-store.ts:76`-`src/main/trace-store.ts:96`). This is relevant for investigations that expect every event to persist.

- **The maps omit that Trace Lab cron traces are reconstructed from local cron output files, not only live trace writes.** `trace-store.ts` scans profile cron output markdown and job metadata into trace runs (`src/main/trace-store.ts:99`-`src/main/trace-store.ts:167`, `src/main/trace-store.ts:218`-`src/main/trace-store.ts:240`). Remote cron behavior may not produce the same local output artifacts.

- **The maps omit synthetic chat mode.** `prepareChatBackend` bypasses runtime preparation in synthetic mode (`src/main/services/chat-service.ts:146`-`src/main/services/chat-service.ts:153`), and `sendMessage` dispatches to `sendSyntheticChatStream` when enabled (`src/main/hermes/gateway.ts:15`-`src/main/hermes/gateway.ts:18`). This affects tests and benchmark behavior.

- **The maps omit the exact updater/menu IPC split.** Updater IPC is registered directly in `src/main/index.ts`, not in `src/main/ipc/*` (`src/main/index.ts:280`-`src/main/index.ts:350`), while menu events are also emitted directly from the menu click handlers (`src/main/index.ts:193`-`src/main/index.ts:210`). Preload receives both in `appApi` (`src/preload/api/app.ts:26`-`src/preload/api/app.ts:93`).

**Trustworthiness summary:** The maps are useful and mostly trustworthy as navigation aids for the current Mercury architecture. The main-process / preload / renderer / CLI split, the runtime/BFF split, and the profile-bound Hermes verification model are all real. The risky parts are overconfident wording around renderer-only `hermesAPI`, IPC argument validation, BFF path safety, cron-service ownership, and remote startup semantics. For changes near Hermes connection, chat persistence, cron, or SSH, treat the maps as an index, not as authoritative behavior documentation; read the cited runtime, chat-service, BFF, and connection files before editing.
