# Investigation: API-only Runtime and Removing CLI Fallback

## Summary
Mercury’s silent local CLI fallback was real and centralized: local runtime resolution could manufacture a verified `transport: "cli"` handle when verified API resolution failed, and gateway dispatch could execute that handle through `chat-cli.ts`. The safest removal path was to make verified API/SSH-API runtime a single central invariant, add bounded API startup retry, remove executable CLI handles/dispatch, and turn runtime verification failures into explicit renderer/CLI errors.

## Implementation status — 2026-05-21

This investigation is now historical/superseded by the API-only runtime implementation. Current behavior requires verified local `api` or SSH `ssh-api` runtime handles for chat/title execution; the internal `chat-cli.ts` fallback transport is removed; CLI commands remain clients of `src/main/services/chat-service.ts` and do not spawn Hermes CLI as a fallback. The detailed findings below remain useful archaeology of the removed behavior.

## Symptoms
- Mercury currently has a local CLI transport fallback for chat when the local API gateway/runtime is not ready or cannot be verified.
- This fallback can allow chat to appear to work while runtime diagnostics remain unverified, masking API readiness/profile-identity failures.
- Desired direction: no silent fallback; chat/title/runtime execution should use verified API runtime only, or fail with an explicit actionable error.

No external research gathered. This is a workspace-local source investigation.

### 2026-05-21 — API-only runtime / no local CLI fallback source trace

#### Fallback inventory

1. **Runtime contract still models CLI as an executable runtime transport.** `RuntimeTransport` includes `"cli"` in both main and shared runtime types (`src/main/hermes/types.ts:17`, `src/shared/runtime.ts:3`), and `ProfileRuntimeRequest.preferTransport` still accepts `"cli"` (`src/main/hermes/types.ts:37-42`). That means API-only behavior is not just a call-site change; the runtime type contract currently permits CLI handles as first-class runtime handles.
2. **`createCliRuntimeHandle(...)` manufactures a verified local identity from CLI args.** The handle sets `actualProfile` to the requested profile, `verified: true`, `verificationSource: "cli-args"`, `mode: "local"`, `transport: "cli"`, and returns `cliCommand` (`src/main/hermes/runtime/identity.ts:30-58`). This is the identity object that lets fallback appear “verified” even though no API runtime was verified.
3. **`ProfileRuntimeManager.resolveRuntime(...)` has two CLI exits.** It immediately returns CLI when `request.preferTransport === "cli"` (`src/main/hermes/runtime/manager.ts:125-127`) and, more importantly, after required local API resolution returns `null`, it returns `apiHandle ?? createCliRuntimeHandle(...)` (`src/main/hermes/runtime/manager.ts:140-141`). `preferTransport: "api"` is only a preference today: for non-`gateway` purposes, failed API resolution falls through to the final API-then-CLI fallback (`src/main/hermes/runtime/manager.ts:129-141`).
4. **Local API verification can fail fast before startup has had time to settle.** `prepareChatBackend(...)` starts the local gateway when it is not running (`src/main/services/chat-service.ts:124-130`) and then immediately calls `resolveRuntime(...)` (`src/main/services/chat-service.ts:133-137`). `startGateway(...)` schedules a readiness check 3 seconds later (`src/main/hermes/runtime/manager.ts:27`, `src/main/hermes/runtime/manager.ts:188-190`), but `resolveLocalApiRuntime(...)` only performs an immediate health probe and returns `null` if not ready (`src/main/hermes/runtime/local-runtime.ts:42-48`). Removing CLI fallback without adding wait/retry will turn normal cold-start races into user-visible failures.
5. **Default-profile API verification has a legacy health-only loophole.** Named profiles require managed-process evidence or return `null` (`src/main/hermes/runtime/local-runtime.ts:33-39`), but the default profile is allowed through `allowLegacyDefaultProbe` (`src/main/hermes/runtime/local-runtime.ts:33-34`). If `/health` returns 200, `resolveLocalApiRuntime(...)` creates a `verified: true` API identity (`src/main/hermes/runtime/local-runtime.ts:50-65`) even when `startedByMercury` is false. For “verified API runtime only,” default profile should either also require managed evidence or be verified by a real identity endpoint rather than `/health` alone (`src/main/hermes/connection.ts:118-144`).
6. **Gateway dispatch has a concrete CLI branch.** `sendMessage(...)` obtains a prepared or freshly resolved runtime (`src/main/hermes/gateway.ts:22-27`), routes `api`/`ssh-api` to `sendMessageViaApi(...)` (`src/main/hermes/gateway.ts:37-45`), and routes `runtime.transport === "cli"` to `sendMessageViaCli(...)` (`src/main/hermes/gateway.ts:48-50`). `chat-cli.ts` then spawns the Hermes Python CLI with profile args, resume args, model args, and profile env/API keys (`src/main/hermes/chat-cli.ts:41-142`).
7. **Chat send inherits fallback through the shared service path.** `runChatMessage(...)` first calls `prepareChatBackend(profile, "chat", resumeSessionId)` (`src/main/services/chat-service.ts:163`), then passes that runtime to `sendMessage(...)` (`src/main/services/chat-service.ts:369-376`). Electron IPC is a thin adapter over the same service: `send-message` invokes `runChatMessage(...)` (`src/main/ipc/chat.ts:50-69`), and preload exposes that invoke as `window.hermesAPI.sendMessage(...)` (`src/preload/api/chat.ts:9-18`).
8. **Title generation is API-execution-only but still silently falls back.** The service prepares a title runtime and passes it into `resolveChatTitle(...)` (`src/main/services/chat-service.ts:424-433`). `generateChatTitle(...)` computes a heuristic fallback first, then uses the prepared runtime or calls `resolveRuntime(... preferTransport: "api")` (`src/main/hermes/title.ts:129-140`). If the runtime is not `api`/`ssh-api`, profile verification fails, or any error is thrown, it returns the heuristic title instead of surfacing runtime verification failure (`src/main/hermes/title.ts:141-149`). This can hide API startup/verification failures even if chat send is made fail-closed.
9. **Renderer UX currently treats idle local unverified runtime as normal/readiness state.** `Layout` suppresses the global diagnostic on Chat when `isIdleLocalUnverifiedRuntime(...)` is true (`src/renderer/src/screens/Layout/Layout.tsx:86-97`, `src/renderer/src/screens/Layout/Layout.tsx:377-381`). `ChatEmpty` shows `ChatRuntimeReadinessCard` only when the conversation is empty (`src/renderer/src/screens/Chat/Chat.tsx:124-137`), and that card starts the gateway then retries `revalidateRuntime` three times (`src/renderer/src/screens/Chat/components/ChatRuntimeReadinessCard.tsx:22-31`, `src/renderer/src/screens/Chat/components/ChatRuntimeReadinessCard.tsx:58-70`). After CLI fallback removal, non-empty chat failure UX needs to show the actionable API runtime error, not rely only on the empty-state readiness card.
10. **CLI adapter does not implement fallback itself.** `mercury chat send` imports the shared chat service and calls `runChatMessage(...)` (`src/cli/chat-commands.ts:225-270`); `mercury chat title` calls `generateChatTitleForRequest(...)` (`src/cli/chat-commands.ts:290-297`). Therefore CLI chat/title will inherit whatever fail-closed behavior the service/runtime layer provides.

#### Risks and edge cases

- **Cold-start regressions:** Without bounded API wait/retry, the first chat after app launch/profile switch can fail because `startGateway(...)` records an unverified started state and schedules readiness later (`src/main/hermes/runtime/manager.ts:161-190`) while chat resolution probes immediately.
- **Default-profile false verification:** Keeping `allowLegacyDefaultProbe` can still mask wrong-process/default-profile API issues because health 200 becomes `verified: true` without managed process evidence (`src/main/hermes/runtime/local-runtime.ts:33-65`).
- **Title UX surprise:** If title generation starts throwing runtime errors, the renderer currently catches title IPC failures and leaves the chat untitled (`src/renderer/src/screens/Chat/hooks/useChatTitleGeneration.ts:59-83`). Product may prefer that over silently persisting heuristic titles, but it should be intentional and visible if runtime failure indicates chat is broken.
- **Error shape drift:** Main IPC currently sends error strings for chat callbacks (`src/main/ipc/chat.ts:58-63`), while CLI can preserve structured codes only if the thrown error exposes `code` (`src/cli/errors.ts:93-116`). If renderer needs actionable codes, add a structured IPC error payload or normalize `ProfileRuntimeError` messages consistently.
- **Dead code/docs drift:** Removing `chat-cli.ts` requires updating docs and tests that currently treat local CLI as profile-correct fallback. Leaving dead CLI code around risks accidental reintroduction.
- **Cron contrast:** Cron remote execution already enforces verified API after resolving runtime (`src/main/cronjobs.ts:134-153`), but because `resolveRuntime(... preferTransport: "api")` can still return CLI, cron depends on a second manual transport check. Runtime manager should make strict API policy central so every caller does not need duplicate guards.

## Root Cause
Mercury currently treats local Hermes CLI execution as a legitimate verified runtime. The type contract permits `transport: "cli"` and `preferTransport: "cli"` (`src/main/hermes/types.ts:17-42`), `createCliRuntimeHandle(...)` creates a verified runtime identity from the selected `-p <profile>` command arguments (`src/main/hermes/runtime/identity.ts:30-58`), and `ProfileRuntimeManager.resolveRuntime(...)` returns that CLI handle either by explicit preference or as the final fallback when local API verification returns `null` (`src/main/hermes/runtime/manager.ts:125-141`).

That fallback then reaches real execution because `src/main/hermes/gateway.ts` imports `sendMessageViaCli(...)` and dispatches `runtime.transport === "cli"` into it (`src/main/hermes/gateway.ts:1-50`). Chat send uses `prepareChatBackend(...)` before dispatch (`src/main/services/chat-service.ts:124-163`), and both Electron IPC and `mercury chat send` use the shared service path. Title generation has a separate masking behavior: it asks for API preference, but runtime failure, non-API runtime, or mismatch all collapse to heuristic title fallback (`src/main/hermes/title.ts:129-149`).

The fallback hides a real cold-start/race problem. `prepareChatBackend(...)` starts the gateway and immediately resolves runtime (`src/main/services/chat-service.ts:124-137`), while `startGateway(...)` records an unverified identity and schedules readiness checking later (`src/main/hermes/runtime/manager.ts:188-213`). If API readiness is not immediate, today the CLI fallback can make chat appear successful while the API runtime remains unverified.

A stricter API-only policy also needs to fix the default-profile verification loophole: `resolveLocalApiRuntime(...)` allows the default profile to verify from a health probe without managed-process evidence (`src/main/hermes/runtime/local-runtime.ts:33-65`). For an API-only runtime, `/health` should prove readiness, not profile identity.

## Recommendations
1. **Make verified API runtime the central invariant.** Change `ProfileRuntimeManager.resolveRuntime(...)` so executable purposes return only verified `api` or `ssh-api` handles, or throw `ProfileRuntimeError`. Remove the final `apiHandle ?? createCliRuntimeHandle(...)` fallback and reject/remove `preferTransport: "cli"`.
2. **Remove executable CLI runtime from the contract.** Remove `"cli"` from new executable `RuntimeTransport` usage and remove/quarantine `createCliRuntimeHandle(...)`. If old traces/diagnostics need to display historical CLI runs, model that separately from current executable runtime handles.
3. **Add bounded local API startup retry before failing.** When local chat/title starts a gateway, retry strict API verification for a bounded window before throwing `runtime-unavailable`. Put this in runtime manager or one manager-owned helper so callers do not duplicate retry logic.
4. **Treat API health separately from identity.** Remove the default-profile health-only verification loophole, or introduce a real API identity endpoint that proves profile/home/port/pid/auth source. `/health` alone should not mark runtime identity verified.
5. **Remove gateway CLI dispatch.** Delete the `sendMessageViaCli` import and `runtime.transport === "cli"` branch from `gateway.ts`; add a defensive shared assertion that runtime is verified `api`/`ssh-api`, has `apiBaseUrl`, and matches requested profile.
6. **Make title fail closed on runtime verification errors.** Keep heuristic fallback for empty input or post-verified model-title failures if desired, but rethrow runtime unavailable/mismatch/unverified/stale errors and do not persist heuristic titles when runtime verification failed.
7. **Preserve structured errors across IPC and CLI.** Runtime setup failure should emit `chat-error`, reject IPC, and produce CLI JSON/NDJSON error envelopes with exit code 4 and diagnostic details. Consider recording failed chat traces for runtime-verification failures.
8. **Update renderer readiness UX.** Change copy to “Chat requires a verified API runtime,” and show actionable verify/debug state for non-empty chats too, not only `ChatEmpty`.
9. **Update tests before implementation.** Replace fallback assertions in runtime, synthetic chat, IPC lifecycle, title, role-runtime, renderer, and CLI tests with strict API-only expectations. Add sentinels preventing `createCliRuntimeHandle`, `preferTransport === "cli"`, `sendMessageViaCli`, or `runtime.transport === "cli"` from reentering execution paths.
10. **Update docs/contracts.** Remove “verified API or CLI fallback” language from connection-mode, chat/tracing, and CLI contract docs; mark older investigations that discuss CLI fallback as historical or superseded.

## Preventive Measures
- Add contract tests that fail if runtime manager can return CLI for chat/title/cron or if gateway imports/calls `sendMessageViaCli`.
- Add cold-start tests proving first chat waits for verified API readiness instead of falling back or failing prematurely.
- Add default-profile identity tests proving health-only readiness cannot masquerade as verified profile identity.
- Add CLI JSON/NDJSON runtime-failure tests asserting exit code 4 and stable error envelopes.
- Add renderer tests for non-empty chat runtime-verification failures with actionable API verification UI.
- Keep runtime policy centralized: callers should request execution; only runtime manager decides whether a verified API runtime exists.
