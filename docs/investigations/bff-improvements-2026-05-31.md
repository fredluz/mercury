# Investigation: BFF Improvements from hermes-web-ui

## Summary
Mercury should implement the BFF improvements, but as an **internal Electron-main `ProfileHermesBffClient`**, not as a browser-visible generic proxy. The investigation confirms Mercury already has the stronger profile/runtime safety model; the main gap is fragmented Hermes HTTP/SSE/retry/diagnostic behavior across multiple modules, plus silent session fallback that weakens the Gateway-as-source-of-truth direction.

## Symptoms
- Mercury may already be profile-aware, but its BFF/proxy/diagnostics story needs comparison against `hermes-web-ui`.
- The target direction is API-first cleanup: renderer must not hold Hermes API keys; main process should be trusted BFF; Hermes Gateway remains source of truth.
- Breaking changes are acceptable if they improve Mercury reliability, speed, and debuggability.

## Background / Prior Research

### External source audit: EKKOLearnAI/hermes-web-ui BFF/proxy
- `packages/server/src/routes/hermes/proxy.ts` registers proxy entrypoints for `/api/hermes/{*any}` and `/v1/{*any}`, with a backup middleware catch-all for the same prefixes.
- `packages/server/src/routes/index.ts` mounts explicit Hermes routes first and returns the proxy middleware to mount last.
- `packages/server/src/routes/hermes/proxy-handler.ts` rewrites `/api/hermes/v1/...` to `/v1/...` and `/api/hermes/...` to `/api/...`.
- The proxy strips incoming `Authorization` and injects `Authorization: Bearer <API_SERVER_KEY>` from profile/gateway resolution; `services/hermes/gateway-manager.ts` reads `API_SERVER_KEY` from the selected profile `.env`.
- Profile selection precedence is `x-hermes-profile` header, `?profile=`, active profile file, then `default`; upstream resolution uses a registered gateway URL or profile host/port config.
- `/v1/runs/{id}/events` is treated as SSE passthrough: raw bytes are streamed to the client while the server parses blocks in parallel.
- Retry behavior appears intentionally small: on transient gateway fetch errors (`ECONNREFUSED`, `ECONNRESET`, fetch failed, socket hang up), poll `/health` for roughly five seconds and retry once.
- Run/session mapping is in-memory: `run_id -> session_id` with TTL cleanup. `POST /v1/runs` captures `session_id`, reads the upstream response to extract `run_id`, then `run.completed` SSE usage can update session usage metadata.
- Inferred limits: no evidence of exponential retry; run/session mapping is ephemeral; SSE interception focuses on usage accounting rather than broad event translation.

### External docs audit: EKKOLearnAI/hermes-web-ui README/docs
- Published docs frame the app as Browser -> Koa BFF -> Socket.IO `/chat-run` -> Hermes agent bridge -> Hermes runtime/CLI/profiles, not as a pure API-server-first app.
- Docker docs state the container uses Hermes CLI/agent bridge and does not start/manage a separate Hermes gateway process.
- README claims multi-profile lifecycle, profile-scoped resources, account/profile authorization boundaries, token/JWT auth, and local SQLite storage for Web UI sessions/group chat.
- Docs describe chat streaming as Socket.IO + bridge; they do not clearly document `/v1/runs` SSE as the primary chat path even though source contains `/v1` proxy/SSE support.
- Visible mismatches: `docs/README.md` is missing/404; README has a port inconsistency (`8648` in architecture, `8647` in dev section).

### Implication for Mercury
The external repo is strongest as a source-level checklist for robust BFF behavior (auth injection, profile/upstream resolution, narrow transient retry, SSE passthrough, run/session metadata interception). Its docs and product architecture are less suitable for direct porting because they emphasize Socket.IO, CLI/bridge execution, local Web UI session ownership, account systems, and deployable web-server concerns that may conflict with Mercury's Electron/API-first direction.

### 2026-05-31 — Mercury BFF/API-first comparison against hermes-web-ui

#### Executive conclusion
Mercury should adopt the **deep module** idea behind hermes-web-ui's BFF — one trusted main-process client that owns URL/auth/retry/SSE/session diagnostics — but **not** its generic HTTP proxy shape or header/query profile routing. Mercury already has a stronger profile-runtime seam than hermes-web-ui: selected-agent runtime identity is resolved by `ProfileRuntimeManager`, proven by managed local/SSH runtime evidence, and consumed through verified runtime handles before execution. The biggest opportunity is to concentrate existing typed wrappers (`runs-api`, `hermes-sessions-api`, cron `/api/jobs`, model inventory/capability probes) behind a single internal main-process BFF client interface so diagnostics/retry/readiness/cache policy live in one place and the renderer never receives arbitrary Hermes endpoint access.

#### Hypothesis results

1. **Proven — do not copy hermes-web-ui header/query profile routing.** Mercury is already strongly profile-aware at the runtime seam. `ProfileRuntimeManager.resolveRuntime(...)` normalizes the requested profile, routes local/SSH/remote modes, and rejects pure remote HTTP as `runtime-unsupported-remote-profile` instead of guessing profile identity (`src/main/hermes/runtime/manager.ts:146-176`). Verified execution requires `assertVerifiedApiRuntimeHandle(...)`, which fails when the handle is missing/non-API, identity is unverified, profile mismatches, API key is invalid, or required capabilities are absent (`src/main/hermes/runtime/api-runtime.ts:12-62`). Local auth is read from the selected profile `.env` (`API_SERVER_KEY`) into `Authorization: Bearer ...` (`src/main/hermes/runtime/local-runtime.ts:291-296`), and SSH auth is cached per normalized profile before being returned as a Bearer header (`src/main/hermes/connection.ts:89-103`). Tests pin this: local unmanaged profiles fail closed (`tests/hermes-runtime.test.ts:127-166`), verified local runtime carries profile-scoped URL/auth evidence (`tests/hermes-runtime.test.ts:181-250`), named SSH through the default port fails closed (`tests/hermes-runtime.test.ts:812-841`), verified SSH requires remote config/status evidence (`tests/hermes-runtime.test.ts:897-957`), and pure remote HTTP fails closed without verified identity (`tests/hermes-runtime.test.ts:959-984`).

2. **Proven — Mercury lacks a generic BFF/proxy layer, and should keep it internal.** The renderer gets a finite `window.hermesAPI` object through `contextBridge`, not raw `fetch` or a generic IPC request method (`src/preload/index.ts:1-17`, `src/preload/api/index.ts:1-17`). The exposed methods are domain calls such as `sendMessage`, `startGateway`, `listSessions`, `listCachedSessions`, and `getRuntimeDiagnostic`, not arbitrary `/v1/*` or `/api/*` paths (`docs/contracts/ipc-preload.md:45-109`). Main IPC registration is explicit by domain (`src/main/ipc/index.ts:13-23`); chat, gateway, system, and sessions handlers accept typed arguments and call services, not a path passthrough (`src/main/ipc/chat.ts:69-161`, `src/main/ipc/gateway.ts:17-38`, `src/main/ipc/system.ts:31-38`, `src/main/ipc/sessions.ts:22-64`). Internal Hermes HTTP is currently split across shallow modules: runs have their own JSON/SSE request helpers (`src/main/hermes/runs-api.ts:362-490`), sessions have another JSON helper (`src/main/services/hermes-sessions-api.ts:112-167`), cron has a `remoteFetch(...)` helper for `/api/jobs` (`src/main/cronjobs.ts:126-158`, `src/main/cronjobs.ts:230-249`), and model inventory still calls `getApiUrl(profile)`/`getRemoteAuthHeader(profile)` directly rather than using a verified runtime handle (`src/main/services/hermes-model-inventory-service.ts:168-216`). That fragmentation is the BFF opportunity.

3. **Proven — retry/readiness/SSE/run-registry behavior exists, but is not centralized enough.** Current strong pieces: local runtime resolution waits for managed PID evidence/readiness and retries bounded startup failures (`src/main/hermes/runtime/manager.ts:422-468`), health polling is per profile and clears after success (`src/main/hermes/runtime/manager.ts:499-509`), runs submission retries run-cap/429-like failures three times (`src/main/hermes/runs-api.ts:191-229`), `HermesRunRegistry` caps active runs at 10 and queues/aborts queued work (`src/main/hermes/run-registry.ts:10-68`), and SSE is consumed from `GET /v1/runs/{id}/events` with `Accept: text/event-stream` and unnamed `data:` JSON blocks (`src/main/hermes/runs-api.ts:298-337`, `src/main/hermes/runs-api.ts:427-490`). Tests cover run submission/SSE/no-chat-completions behavior (`tests/hermes-runs-api.test.ts:106-165`), terminal-status polling when SSE closes early (`tests/hermes-runs-api.test.ts:167-207`), debug-prompt remediation for `run.failed` (`tests/hermes-runs-api.test.ts:209-253`), and queue capacity (`tests/hermes-run-registry.test.ts:17-78`). Weakness: retry/readiness logic is distributed between runtime manager, runs transport, renderer readiness card, gateway service, and sessions diagnostics. Example: the renderer readiness card has its own three-attempt `revalidateRuntime` loop plus start/restart logic (`src/renderer/src/screens/Chat/components/ChatRuntimeReadinessCard.tsx:32-47`), while gateway service has a separate five-attempt revalidation loop (`src/main/services/gateway-service.ts:29-68`), and sessions diagnostics have their own NDJSON writer (`src/main/services/sessions-service.ts:47-119`). A main-process BFF client should make these policies one interface.

4. **Partially proven — legacy/non-API paths are mostly isolated, but not cleaned up enough for “Gateway is source of truth.”** Chat is API-only: `sendMessageViaApi(...)` delegates to the runs API (`src/main/hermes/chat-api.ts:1-16`), `/v1/chat/completions` is deliberately absent and docs say there is no fallback (`docs/subsystems/chat-and-tracing.md:354-364`, `docs/subsystems/chat-and-tracing.md:442-444`), and CLI docs state local chat exits with a runtime error instead of spawning Hermes CLI fallback (`docs/contracts/cli.md:351-356`). Contract tests prevent reintroducing `sendMessageViaCli`, `chat-cli.ts`, `createCliRuntimeHandle`, executable `transport: "cli"`, or `/v1/chat/completions` (`tests/reliable-profile-runtime-contract.test.ts:15-66`, `tests/reliable-profile-runtime-contract.test.ts:124-149`; docs summary at `docs/testing/contract-tests.md:506-517`). However, sessions still fall back to local DB/cache on API errors: list sessions falls back from `listHermesSessions(runtime)` to `listSessionsForProfile(...)` (`src/main/services/sessions-service.ts:144-164`), message fetch falls back to local DB after Hermes session read/messages fail (`src/main/services/sessions-service.ts:176-184`), and title update falls back to local `updateSessionTitle(...)` (`src/main/services/sessions-service.ts:287-294`). The cache itself is profile-aware and efficient (`src/main/session-cache.ts:316-382`; duplicate IDs across profiles covered by `tests/session-cache-sync.test.ts:365-467`), but it is still a mixed source-of-truth path rather than a pure read-through cache of Hermes Gateway state.

#### Flow evidence

Chat methods invoke fixed channels and listen to fixed event channels (`src/preload/api/chat.ts:6-105`). Gateway/session methods are fixed calls on `navigationApi` (`src/preload/api/navigation.ts:32-82`); cache/session-search/model-auth calls are fixed calls on `modelsApi` (`src/preload/api/models.ts:39-96`); runtime diagnostic/revalidation/debug launch are fixed calls on `appApi` (`src/preload/api/app.ts:16-24`). No hidden generic proxy/passthrough was found.

- **Profile runtime resolution and auth injection.** Chat service prepares the selected profile backend: starts/restarts local gateway if needed, ensures SSH tunnel/gateway/key when in SSH mode, then resolves the runtime through `ProfileRuntimeManager` (`src/main/services/chat-service.ts:145-203`). #### Eliminated hypotheses

- **Hidden generic Hermes proxy/passthrough exists:** eliminated. Searches and spot checks found only typed preload/IPC channels and internal main-process request helpers with fixed callsites, not renderer-controlled arbitrary paths (`src/preload/api/index.ts:9-16`, `src/main/ipc/index.ts:13-23`, `src/main/hermes/runs-api.ts:246-300`, `src/main/services/hermes-sessions-api.ts:192-279`).
- **Renderer should send profile headers/query params like hermes-web-ui:** eliminated for local/SSH execution. Mercury proves selected profile through runtime identity, managed process/port/PID/config evidence, and per-profile auth headers; adding renderer-controlled profile headers would be a weaker, spoofable seam (`src/main/hermes/runtime/api-runtime.ts:12-62`, `src/main/hermes/runtime/manager.ts:146-176`).
- **Chat still has `/v1/chat/completions` or Hermes CLI fallback:** eliminated for current chat/title execution. The compatibility path is absent by source and guarded by tests/docs (`src/main/hermes/chat-api.ts:1-32`, `docs/subsystems/chat-and-tracing.md:354-364`, `tests/reliable-profile-runtime-contract.test.ts:15-66`).
- **Session cache is default-only/unprofiled:** mostly eliminated. The cache is now profile-aware and duplicate-safe (`src/main/session-cache.ts:316-382`, `tests/session-cache-sync.test.ts:365-467`). Remaining issue is not profile loss but mixed source-of-truth fallback behavior.

#### Implementation plan

1. **Introduce an internal `ProfileHermesBffClient` main-process module.** Construction requires a `VerifiedApiRuntimeHandle`; expose typed subclients (`runs`, `sessions`, `jobs`, `capabilities`, `models`) and one shared request layer for JSON, SSE, timeout, auth, redaction, request IDs, and structured error classification. Do not expose `request(path)` through preload or IPC.
2. **Move existing wrappers behind the BFF client.** Port `runs-api.ts`, `hermes-sessions-api.ts`, cron `remoteFetch(...)`, capability probing, and model inventory API access to the shared client. This converts several shallow modules into adapters behind one deeper seam and removes direct `getApiUrl(profile)`/`getRemoteAuthHeader(profile)` calls from model inventory.
3. **Centralize readiness and retry policy.** Keep fail-closed profile verification. Add one transient-network policy inspired by hermes-web-ui (small health/capability recheck then one retry) for idempotent JSON calls and run submission where safe; keep run-cap retry/queue in the runs layer; keep SSE as a single live stream unless Hermes adds resumable event cursors.
4. **Make diagnostics first-class on every BFF call.** Emit redacted metadata for endpoint family, profile, runtime identity fingerprint, status code, retry count, readiness/capability problem, run/session id, and duration. Fold `MERCURY_SESSIONS_DIAG`-style output into a shared diagnostic sink instead of per-service logging.
5. **Tighten sessions toward Hermes Gateway as source of truth.** Reframe local DB/cache as explicit offline/legacy adapters. For normal verified API runtimes, prefer `/api/sessions` and make fallback opt-in/diagnostic-visible rather than silent. Keep the desktop cache as a read-through performance cache keyed by `(profile,id)`, not a competing source.
6. **Isolate or remove legacy/non-API execution.** Leave local file/CLI adapters only where Hermes Gateway lacks a typed API or for explicit offline maintenance. Chat/title should stay API-only; title currently uses a heuristic fallback only (`src/main/hermes/title.ts:13-23`) and should either stay intentionally local or gain a typed Gateway title endpoint later, not resurrect chat-completions.
7. **Extend contract tests.** Add sentinels that forbid renderer raw proxy methods, require BFF-client use for all Hermes HTTP families, require model inventory to use verified runtime identity, assert no silent session API fallback in verified online mode, and assert diagnostic records for transient retry/SSE/status-poll failures.

#### Recommendation
Proceed aggressively with an **internal API-first BFF client**, not a hermes-web-ui-style public proxy. The target architecture should preserve Mercury's stronger profile-runtime proof while concentrating Hermes Gateway access into one main-process module for locality, leverage, diagnostics, and speed.

## Root Cause
Mercury does not need a public BFF proxy; it already has a safer Electron boundary and verified profile runtime model. The root architectural issue is **missing consolidation**: Hermes Gateway access is spread across several main-process helpers, each with its own request construction, auth injection, timeout/retry behavior, parsing, and diagnostics. That fragmentation makes failures harder to debug, creates inconsistent readiness behavior, and lets some paths (notably sessions/model inventory) drift from the API-first/Gateway-source-of-truth model.

## Recommendations
1. **Create an internal `ProfileHermesBffClient` requiring `VerifiedApiRuntimeHandle`.** It should own base URL normalization, auth header injection, request IDs, timeouts, secret redaction, structured `HermesBffError`, diagnostics ledger, and typed JSON/SSE helpers.
2. **Keep preload/IPC typed; do not expose a raw `/v1/*` or `/api/*` proxy.** Add guardrail tests proving renderer cannot pass arbitrary Hermes paths, headers, auth, or profile selectors.
3. **Port API families behind typed BFF subclients in this order:** sessions first, runs/SSE second, idempotent retry third, run orchestrator fourth, jobs/models/capabilities fifth, remote declared-profile support last.
4. **Make sessions Gateway-authoritative in verified online mode.** Local DB/cache should be read-through performance cache or explicit offline/legacy mode, never silent fallback.
5. **Centralize bounded retry.** Retry once on narrow transient transport failures after short health recovery; never retry profile mismatch, invalid auth, missing capabilities, unverified runtime, or unsafe POSTs without idempotency/client-run IDs.
6. **Replace runs-local SSE parsing with shared BFF SSE infrastructure.** Preserve typed renderer events, but keep bounded redacted raw snippets and stream metadata for diagnostics.
7. **Evolve `HermesRunRegistry` into a run orchestrator.** Track client run id, Hermes run id, profile, session id, trace run id, renderer target, runtime fingerprint, status, abort controller, approvals, and timestamps.
8. **Do not port hermes-web-ui’s incompatible architecture:** Socket.IO `/chat-run`, CLI/agent bridge execution, browser-visible generic proxy, renderer-controlled `x-hermes-profile` / `?profile=`, account/JWT model, Web UI-owned SQLite sessions, broad retry, or `/v1/chat/completions` fallback.

## Preventive Measures
- Add contract tests forbidding direct Hermes HTTP outside the approved BFF module, except explicitly allowlisted low-level probes during migration.
- Add tests that model inventory and sessions use verified runtime identity in online mode.
- Add diagnostics snapshot tests for transient retry, SSE premature close/status-poll, invalid auth, missing capabilities, and session API failure.
- Document the BFF boundary in `docs/subsystems/chat-and-tracing.md` and `docs/contracts/ipc-preload.md` once implemented.
- Require new Hermes Gateway endpoints to be added as typed BFF subclient methods rather than one-off HTTP helpers.
