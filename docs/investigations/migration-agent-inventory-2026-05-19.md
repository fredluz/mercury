# Investigation: Agent Inventory for Hermes and OpenClaw Migration

## Summary
Mercury has enough profile-scoped Hermes readers to build explicit profile-as-agent candidate cards, but the new migration goal needs a separate root-parameterized, read-only inventory domain. That domain should scan arbitrary old Hermes/OpenClaw installs, normalize evidence into candidate-agent records, redact sensitive content, synthesize possible agents from memories/skills/sessions/tasks/channels, and produce a user-selectable plan before any mutation.

## Symptoms
- Migration should not only copy files; it should help identify what useful agents or agent-like workspaces are hidden in previous installations.
- Users need to know which persistent agents/profiles exist, what skills they have, what memories/persona files they carry, and what tasks/sessions they have been used for.
- Candidate agents should not be limited to existing profile/agent IDs. Mercury should be able to infer or distill possible agents from skills, memory clusters, prompts, recurring tasks, session/task histories, channel identities, and other persistent traces, then present a reasonable user-pickable list.
- Hermes and OpenClaw store agent state differently, so Mercury may need different inventory prompts/planners for each source.

## Background / Prior Research
- Prior migration report: `docs/investigations/migration-hermes-openclaw-2026-05-19.md` found Mercury currently has Hermes archive import and a coarse OpenClaw migration shell-out, but not a first-class migration planner/inventory flow.
- Hermes skill notes: Hermes profiles are isolated homes under `~/.hermes` or `~/.hermes/profiles/<name>`, each with its own config, env, memory, sessions, skills, and gateway service.

### Hermes persistent-agent inventory research
- Treat each Hermes profile home as an agent workspace identity. Primary root is `~/.hermes` or `HERMES_HOME`; named profiles live at `~/.hermes/profiles/<name>/`.
- Per-profile inventory candidates: `config.yaml`, `.env` presence, `SOUL.md`, `memories/MEMORY.md`, `memories/USER.md`, `state.db` plus WAL/SHM, `skills/`, `cron/jobs.json`, `cron/output/*`, `logs/agent.log`, `logs/gateway.log`, `logs/errors.log`, `gateway.pid`, and optional/version-dependent `sessions/`, `plugins/`, `plans/`, MCP config, or global/shared `auth.json`.
- Session/task history signal is primarily SQLite `state.db`: `sessions`, `messages`, FTS tables, tool-call metadata, reasoning fields, model/source/platform/title/token/cost stats, and schema migrations. Legacy `sessions/` can be supplemental.
- Skills are directory-based and described by `SKILL.md` frontmatter/content. Usage signals may live in a skills sidecar such as `.usage.json` with counts and recent activity, depending on version.
- Useful validation/enumeration commands include `hermes profile list`, profile targeting with `-p`, `hermes skills list`, `hermes sessions list|browse|stats|export`, `hermes cron list`, `hermes logs`, `hermes dump`, and `hermes gateway status`.
- Migration-safe scanner rule: inventory first, redact secrets by default, summarize session/task history from local DB content, flag shared/global credential artifacts separately, and treat profile collisions as planner concerns rather than immediate copy operations.
- Follow-up: Hermes supports candidate-agent inference beyond real profiles. Seed one candidate per real profile, then synthesize additional candidates from session clusters by source/platform/topic, repeated cron prompt/skill combinations, skill-usage bundles, and memory/persona theme clusters. Candidate names can come from profile names, SOUL first heading/line, frequent session title phrases, or cron job names. Capability signals include installed skills, referenced scripts, tool-call frequencies from messages, model/provider choices, recurring cron tasks, and delivery targets. Confidence can be high for explicit profile+SOUL+history, medium for stable behavior clusters, and low for sparse traces.
- Minimal user-pickable Hermes candidate shape: candidate ID, origin (`profile` or `synthesized`), display name, confidence, source profiles, persona summary, capability summary, use-case summary, activity counts/date ranges/platform mix, and privacy flags for secrets/PII/raw transcript consent.

### OpenClaw candidate-agent inventory research
- Do not only enumerate configured `agentId`s. Build a read-only evidence graph from OpenClaw roots and cluster candidate agents from configured agents, workspace persona files, memory/topic clusters, recurring tasks, session/channel clusters, and skill-capability bundles.
- Strong identity/persona files in each workspace can include `AGENTS.md`, `SOUL.md`, `IDENTITY.md`, `USER.md`, `TOOLS.md`, `HEARTBEAT.md`, `BOOTSTRAP.md`, `MEMORY.md`, `DREAMS.md`, and dated memory notes such as `memory/YYYY-MM-DD.md`.
- Behavioral/task history signals include per-agent `~/.openclaw/agents/<agentId>/sessions/sessions.json`, `~/.openclaw/agents/<agentId>/sessions/*.jsonl`, session keys/display names/provider/room/subject, recency/frequency, tool-heavy patterns, compaction/memory-flush cadence, cron jobs, cron run logs, and a detached task ledger such as `$OPENCLAW_STATE_DIR/tasks/runs.sqlite`.
- Capability signals come from skills roots and precedence: workspace `skills`, workspace `.agents/skills`, global `~/.agents/skills`, `~/.openclaw/skills`, bundled skills, and configured `skills.load.extraDirs`, plus any allowlists/overrides.
- Audience/channel signals come from multi-agent/channel bindings, routing keys, account-scoped identities, and channel targets. These can imply agent personas such as operations bot, personal assistant, support responder, or monitoring/reporting agent.
- Candidate output should include candidate name, confidence, evidence paths/fields, skills summary, memory summary, past use cases, redacted channel identities, and last active time. Secrets from `auth-profiles.json`, `credentials/`, `.env`, and config env blocks must be redacted; phone/chat/account IDs/emails/tokens should be redacted or hashed.
- Useful read-only commands: `openclaw status --all`, `openclaw agents list --bindings --json`, `openclaw sessions --all-agents --json`, `openclaw cron list`, `openclaw cron runs --id <jobId>`, `openclaw channels list`, `openclaw channels status --probe`, `openclaw memory status --deep`, `openclaw memory search`, and `openclaw doctor` for legacy-layout normalization checks.

### Phase 2 - Mercury primitives audit (2026-05-19)

#### Hypothesis verdict
- **Confirmed.** Mercury has enough Hermes/Mercury profile-scoped primitives to seed explicit candidate cards for existing Hermes profiles: profile names/paths, model/provider hints, `.env`/SOUL presence, installed skills, gateway state, memory/user files, cron jobs, and profile-scoped session metadata are all readable today.
- **Confirmed missing pieces.** Those readers are mostly parameterized by `profile?: string`, not by arbitrary source root, and profile resolution is hard-wired through `profileHome(profile)` to `HERMES_HOME` or `HERMES_HOME/profiles/<name>` (`src/main/utils.ts:22-26`). Mercury therefore lacks root-parameterized scanners for external Hermes homes and OpenClaw roots.
- **Confirmed for OpenClaw.** Current OpenClaw support is only coarse directory detection plus a Hermes CLI shell-out. There is no Mercury-owned scanner for OpenClaw persona/memory/session/task/skills/channel artifacts.
- **Confirmed for synthesized agents.** Current code can expose signals that would help synthesize candidates, but it has no candidate-agent inference layer, shared inventory/plan data model, candidate-card API, or migration-specific privacy/redaction policy.

#### Hermes profile candidate evidence already available
- Profile discovery already creates a useful explicit profile card seed: `ProfileInfo` includes `name`, `path`, `isDefault`, `isActive`, `model`, `provider`, `hasEnv`, `hasSoul`, `skillCount`, and `gatewayRunning` (`src/main/profiles.ts:15-26`). `listProfiles()` reads the default profile from `HERMES_HOME`, named profiles from `HERMES_HOME/profiles`, config/model/provider, `.env`, `SOUL.md`, skills, and gateway PID (`src/main/profiles.ts:106-181`).
- The core profile-home mapping is simple enough for an inventory planner to reproduce: default/undefined maps to `HERMES_HOME`, named profiles map to `HERMES_HOME/profiles/<name>` (`src/main/utils.ts:22-26`). This supports explicit Hermes profile candidates, but only inside Mercury's configured `HERMES_HOME`.
- Memory and persona files are already profile-scoped: `readMemory(profile?)` reads `memories/MEMORY.md`, `memories/USER.md`, and counts sessions/messages from profile `state.db` (`src/main/memory.ts:34-40`, `src/main/memory.ts:78-129`); `readSoul(profile?)` reads profile-root `SOUL.md` (`src/main/soul.ts:12-20`).
- Skills are already profile-scoped for installed skills: `listInstalledSkills(profile?)` walks `<profileHome>/skills/<category>/<skill>/SKILL.md`, parses frontmatter, and returns name/category/description/path (`src/main/skills.ts:64-116`). `getSkillMetadata(skillPath)` can summarize associated scripts/references for a selected skill path (`src/main/skills.ts:129-203`).
- Cron jobs are profile-scoped in local mode: `jobsFilePath(profile?)` points to `<profileHome>/cron/jobs.json`, and normalized job fields include id/name/schedule/prompt/state/next/last status/delivery targets/skills/script (`src/main/cronjobs.ts:13-30`, `src/main/cronjobs.ts:32-67`, `src/main/cronjobs.ts:113-166`). Those fields are strong synthesized-agent signals for recurring tasks, skill bundles, and channel/delivery targets.
- Config/env/model/platform readers already use profile paths for the active Mercury home: `readEnv`, `getConfigValue`, `getModelConfig`, and `getPlatformEnabled` all flow through `profilePaths(profile)` (`src/main/config.ts:100-144`, `src/main/config.ts:179-190`, `src/main/config.ts:213-239`, `src/main/config.ts:299-318`). These can supply model/provider/platform hints for a candidate card, but `.env` values must not be exposed.

#### Safe session/task-history metadata and limits
- Local session list reads only `sessions.id`, `source`, `started_at`, `ended_at`, `message_count`, `model`, and `title` from each profile's `state.db` (`src/main/sessions.ts:50-86`). This is enough for a redacted activity summary: profile, source, model mix, title presence, started/ended ranges, and message counts.
- Cross-profile session aggregation already exists: `discoverSessionProfileScopes()` returns the default profile plus directories under `HERMES_HOME/profiles`, each with a `state.db` path (`src/main/session-db.ts:17-56`), and `listSessions()` aggregates/sorts scopes when no profile is specified (`src/main/sessions.ts:87-98`). This proves the explicit Hermes-profile inventory can summarize multiple profile histories.
- Session cache mirrors safe-ish fields (`id`, `title`, `startedAt`, `source`, `messageCount`, `model`, `profile`) under `HERMES_HOME/desktop/sessions.json` (`src/main/session-cache.ts:18-27`, `src/main/session-cache.ts:143-157`). It is fast for UI but should be treated as derived state, not the authoritative migration inventory.
- Missing session metadata for candidate inference: current TypeScript readers do **not** expose tool names, platform/channel, token counts, or costs from `state.db`; the supported session row shape is source/model/title/date/message-count only (`src/main/sessions.ts:50-86`, `src/main/session-cache.ts:89-110`). Tool/platform inference would require direct upstream Hermes schema inspection beyond the current reader or a new query layer.
- Privacy caveat: session titles may be generated from the first user message when `sessions.title` is absent (`src/main/session-cache.ts:117-147`), session search returns FTS snippets from message content (`src/main/sessions.ts:137-170`), and `getSessionMessages()` returns raw user/assistant content (`src/main/sessions.ts:224-258`). Candidate inventory should default to counts/date ranges/source/model and either omit titles/snippets or label them as transcript-derived and require opt-in.

#### Root-parameterization gaps
- The best candidates for root-generalization are pure filesystem/SQLite readers: memory (`src/main/memory.ts:34-40`, `src/main/memory.ts:78-108`), soul (`src/main/soul.ts:12-20`), installed skills (`src/main/skills.ts:64-116`), config/env/model/platform (`src/main/config.ts:100-144`, `src/main/config.ts:213-239`, `src/main/config.ts:299-318`), local cron (`src/main/cronjobs.ts:28-30`, `src/main/cronjobs.ts:146-166`), and session DB paths (`src/main/session-db.ts:17-34`).
- However, all of those ultimately route through `profileHome(profile)`, which is bound to Mercury's `HERMES_HOME` (`src/main/utils.ts:22-26`). The profile subsystem also anchors discovery to `PROFILES_DIR = join(HERMES_HOME, "profiles")` and the active profile file under `HERMES_HOME` (`src/main/profiles.ts:13`, `src/main/profiles.ts:87-94`, `src/main/profiles.ts:106-181`).
- Tighter global bindings need deliberate migration semantics: desktop connection config lives in `HERMES_HOME/desktop.json` (`src/main/config.ts:26-78`), while the credential pool lives in global `HERMES_HOME/auth.json`, not a profile root (`src/main/config.ts:378-421`). A migration planner should flag these as global/shared artifacts instead of silently copying them into profile candidates.
- Several operations shell out to Hermes using global `HERMES_HOME`, `HERMES_REPO`, `HERMES_SCRIPT`, and `HERMES_PYTHON` rather than reading arbitrary roots: profile create/delete (`src/main/profiles.ts:184-236`), skill search/install/uninstall (`src/main/skills.ts:219-260`, `src/main/skills.ts:318-374`), and cron mutations (`src/main/cronjobs.ts:168-194`). These should remain apply-time/execution primitives, not inventory readers.

#### OpenClaw support is not an evidence reader
- Detection only checks for `~/.openclaw`, `~/.clawdbot`, or `~/.moldbot` and returns the first existing path (`src/main/install/paths.ts:284-293`). It does not honor `OPENCLAW_STATE_DIR`, `OPENCLAW_CONFIG_PATH`, profile-style roots, workspace roots, or config files.
- Execution checks that Hermes exists, calls the coarse detector, and spawns `HERMES_PYTHON` with `[HERMES_SCRIPT, "claw", "migrate", "--preset", "full"]` (`src/main/install/executor.ts:12-49`). Mercury does not inspect OpenClaw memory/persona/session/task/skills/channel files before running it.
- Service, IPC, preload, and CLI surfaces preserve the same no-argument shape: `checkOpenClaw()` / `runClawMigrateForConnection()` (`src/main/services/install-service.ts:126-138`), IPC channels `check-openclaw` and `run-claw-migrate` (`src/main/ipc/install.ts:56-62`), preload `checkOpenClaw()` and `runClawMigrate()` (`src/preload/api/install.ts:66-70`, `src/preload/index.d.ts:71-73`), and CLI `mercury claw migrate` (`src/cli/mutating-commands.ts:507-535`, `docs/contracts/cli.md:1245-1269`).
- The `openclaw` CLI domain is reserved but unimplemented (`src/cli/index.ts:34-64`, `docs/contracts/cli.md:1284-1288`). This is a good namespace for future read-only `openclaw inventory` or broader `migration plan` commands, but there is no direct scanner today.
- **Eliminated hypothesis:** Mercury already owns OpenClaw artifact mapping. Current code delegates mapping entirely to upstream Hermes' `claw migrate --preset full`, so Mercury cannot currently produce user-pickable OpenClaw candidate cards before apply.

#### Synthesized candidate signals and missing inference layer
- Mercury traces have some reusable inference signals: trace event types include tool, delegation, artifact, approval, usage, and skill lifecycle events (`src/shared/traces.ts:1-29`), and `TraceRun` stores profile, title, status, timestamps, session id, message preview, events, and token/cost usage (`src/shared/traces.ts:31-65`).
- The trace store already sanitizes event titles/details and metadata, drops metadata keys matching API key/token/authorization/secret/password/credential, caps metadata/detail lengths, and caps persisted runs/events (`src/main/trace-store.ts:19-24`, `src/main/trace-store.ts:83-121`, `src/main/trace-store.ts:145-170`). This is useful prior art for a migration redaction helper.
- But trace storage is Mercury-current and global under `HERMES_HOME/desktop-traces.json`, not a scanner for historical Hermes/OpenClaw roots (`src/main/trace-store.ts:19-24`). It also stores `messagePreview`, so it is not automatically safe for migration cards without redaction/consent (`src/shared/traces.ts:52-63`).
- No shared `MigrationInventory`, `CandidateAgent`, `MigrationPlan`, or `MigrationApply` type exists in `src/shared`, and the only `candidate` terminology found in current source is trace/skill status, not migration-agent candidates (`src/shared/traces.ts:60-65`, `src/main/trace-store.ts:352-355`).
- Recommended synthesized-agent evidence graph: combine explicit profile/agent identities, SOUL and memory headings/summaries, installed skill bundles, cron prompt+skills+delivery clusters, session metadata clusters by source/model/title phrase/date range, trace tool/skill/delegation signals where available, and redacted channel/platform hints. Each edge should carry evidence paths and privacy class.

#### Privacy and redaction boundaries
- Treat `.env`, `auth.json`, `desktop.json` remote API keys, credential directories, `auth-profiles.json`, and OpenClaw credential folders as **secret artifacts**. Current code can read profile `.env` values directly (`src/main/config.ts:113-144`) and global credential pool entries from `auth.json` (`src/main/config.ts:378-421`), so inventory must report presence/provider labels only unless the user explicitly opts into secret migration.
- Treat raw sessions, FTS snippets, generated titles from first user messages, prompt text, cron prompts, trace `messagePreview`, chat/account IDs, phone numbers, emails, channel room IDs, logs, and gateway/platform config as **PII or transcript-derived artifacts**. The default candidate card should show counts, recency, platforms/source labels, and short redacted summaries rather than raw values.
- Existing redaction is partial and local to specific features: runtime debug redacts the remote API key in its generated prompt (`src/main/services/runtime-debug-service.ts:63-70`), and trace-store metadata sanitization drops secret-looking keys (`src/main/trace-store.ts:83-121`). There is no central migration redaction model with artifact classes, hashing policy, consent gates, or audit output.
- Recommended boundary: inventory can always show artifact existence, counts, sizes, modified times, profile/agent IDs after normalization, and hashed external identifiers. Showing raw prompt/session/log/channel/email/phone values should require per-plan opt-in and be excluded from default exported reports.

#### API, CLI, and UI insertion points
- Add planner/apply methods beside the current install migration wrapper in `src/main/services/install-service.ts:126-138`, e.g. `inventoryMigrationSources`, `planHermesAgentInventory`, `planOpenClawAgentInventory`, and `applyMigrationPlan`.
- Add main-process scanner modules rather than extending install executor directly, e.g. `src/main/migration/hermes-inventory.ts`, `src/main/migration/openclaw-inventory.ts`, and shared types in `src/shared/migration.ts`. The executor's shell-out should become apply-time only after a user accepts a plan (`src/main/install/executor.ts:38-49`).
- Wire plan/apply through `src/main/ipc/install.ts:17-62`, `src/preload/api/install.ts:4-70`, `src/preload/api/index.ts:9-16`, and `src/preload/index.d.ts:39-74`. The current preload API shape proves the install fragment is the right bridge but lacks parameters and plan result types.
- Add read-only CLI planning under `src/cli/read-only-commands.ts:268-304` and mutating apply under `src/cli/mutating-commands.ts:507-535`. Either use the existing reserved `openclaw` domain or add a documented `migration` domain in `src/cli/index.ts:34-64` and `docs/contracts/cli.md`.
- Replace the Settings OpenClaw banner-only flow with a two-phase inventory/results panel. Current state and actions live in `src/renderer/src/screens/Settings/Settings.tsx:59-76` and `src/renderer/src/screens/Settings/Settings.tsx:156-201`; current rendering is a simple migration banner in `src/renderer/src/screens/Settings/components/SettingsCoreSections.tsx:392-444`; existing CSS can be extended from `.settings-migration-banner` and actions (`src/renderer/src/assets/styles/settings.css:250-303`). Candidate cards should expose confidence, origin, evidence paths, privacy flags, and selected target profile/agent mapping.

#### Concrete recommendations
1. **Create a migration inventory domain model.** Minimum shared shapes: `MigrationSourceRoot`, `InventoryArtifact`, `CandidateAgent`, `CandidateEvidence`, `PrivacyFlag`, `MigrationPlan`, `MigrationPlanSelection`, and `MigrationApplyResult`.
2. **Parameterize readers by source root.** Refactor pure readers to accept `{ root: string }` or introduce scanner-specific equivalents; do not overload `profile?: string` for external roots.
3. **Build Hermes inventory first.** It can produce high-confidence explicit candidates from existing profile homes using current primitives, then add medium/low-confidence synthesized candidates from cron, skills, sessions, memory/SOUL, and traces.
4. **Build OpenClaw inventory as a separate scanner.** Do not rely on `hermes claw migrate --preset full` for preview. Read OpenClaw config/state roots directly, detect agents/workspaces/channels/skills/credentials, and only use upstream migrate/apply after candidate selection.
5. **Make redaction central and testable.** Use trace-store sanitization as prior art, but add migration-specific artifact classes, denylisted filenames, hash/redact helpers, and tests for `.env`, `auth.json`, `credentials/`, raw sessions, logs, channel IDs, emails, phone numbers, and prompt text.
6. **Treat synthesized agents as recommendations, not imports.** Candidate cards should state confidence and evidence, require user selection, and default to explicit profiles/agents before inferred clusters.
7. **Add contract tests before UI work.** Cover root scanning without mutation, no raw transcript leakage by default, OpenClaw alternate-root detection, candidate confidence/evidence paths, target-profile collision handling, and CLI/IPC/preload parity for plan/apply.

#### Eliminated / qualified hypotheses
- **“Mercury lacks all profile-scoped Hermes primitives.”** Eliminated. Profiles, memory/SOUL, skills, cron, config/env, and sessions are profile-scoped enough for explicit Hermes profile candidate cards.
- **“Existing session metadata is safe by default.”** Qualified. The list/cache rows are mostly safe, but title generation, search snippets, and message retrieval can expose prompt/transcript content.
- **“Session metadata includes tool/platform/token/cost for inventory.”** Eliminated for the current TS readers. Tool/platform/token/cost require trace data or deeper upstream DB/schema readers.
- **“OpenClaw migration support can inventory candidates today.”** Eliminated. It only detects fixed home directories and shells to Hermes.
- **“Trace redaction solves migration privacy.”** Eliminated. It is useful prior art, but there is no central migration redaction/consent model.
- **“A candidate-card API already exists.”** Eliminated. Existing install APIs expose only check/run and backup/import, not inventory/plan/apply candidate structures.

## Root Cause
Mercury has profile-scoped operational readers and coarse migration executors, but no root-parameterized, read-only migration inventory domain that can inspect arbitrary old Hermes/OpenClaw sources, normalize evidence, redact sensitive data, synthesize candidate agents, and produce a user-selectable plan.

For Hermes, current code can describe profiles inside Mercury's active `HERMES_HOME`: `listProfiles()` reports profile path, model/provider, `.env` presence, SOUL presence, skill count, and gateway status (`src/main/profiles.ts:15-26`, `src/main/profiles.ts:106-181`). Memory, SOUL, skills, cron, config, and session readers provide useful evidence, but they take `profile?: string` and ultimately resolve through `profileHome(profile)` to `HERMES_HOME` or `HERMES_HOME/profiles/<name>` (`src/main/utils.ts:22-26`). That is sufficient for explicit profile cards in the current home, not for scanning arbitrary old Hermes roots.

For OpenClaw, Mercury does not have an evidence reader. It detects only fixed directories (`~/.openclaw`, `~/.clawdbot`, `.moldbot`) and shells to `hermes claw migrate --preset full` (`src/main/install/paths.ts:284-293`, `src/main/install/executor.ts:12-49`). It cannot currently inspect OpenClaw persona files, memories, sessions/jsonl, cron/task ledgers, skill roots, channel bindings, or credentials to present candidate agents before apply.

The new requirement also introduces privacy and inference concerns that current APIs do not model. Session list rows expose relatively safe metadata (`id`, `source`, started/ended times, message count, model, title), but search returns FTS snippets, message APIs return raw transcripts, and session cache can generate titles from first user messages (`src/main/sessions.ts:50-86`, `src/main/sessions.ts:137-170`, `src/main/sessions.ts:224-258`, `src/main/session-cache.ts:117-147`). Credential data is mixed: `.env` is profile-scoped but value-sensitive, while the credential pool is global at `HERMES_HOME/auth.json` (`src/main/config.ts:378-421`). Existing redaction helpers in trace/debug code are useful prior art, not a migration-specific privacy model (`src/main/trace-store.ts:83-121`, `src/main/services/runtime-debug-service.ts:63-70`).

## Eliminated / Qualified Hypotheses
- **“Hermes migration inventory has no usable primitives.”** Eliminated. Mercury has enough profile-scoped readers for explicit Hermes profile candidates.
- **“Hermes profiles equal all candidate agents.”** Qualified. Hermes profiles are the strongest current proxy for persistent agents, but synthesized candidates may also emerge from session clusters, skills, memory themes, cron tasks, and platform/source patterns.
- **“OpenClaw can be inventoried by current Mercury migration support.”** Eliminated. Current support only detects fixed directories and runs an upstream shell-out.
- **“Current session metadata is safe by default.”** Qualified. Counts/date/source/model are safer; titles, snippets, raw messages, prompts, and logs are transcript-derived and need consent/redaction.
- **“Trace redaction solves migration privacy.”** Eliminated. It is prior art only; migration needs artifact classes, hashing/redaction policy, and tests.

## Recommendations
1. **Define shared migration inventory contracts first.** Add types such as `MigrationSourceRoot`, `MigrationSourceKind`, `InventoryArtifact`, `CandidateAgent`, `CandidateEvidence`, `PrivacyFlag`, `CandidateConfidence`, `MigrationConflict`, `MigrationPlan`, `MigrationPlanSelection`, and `MigrationApplyResult`, likely under `src/shared/migration.ts`.
2. **Do not overload `profile?: string` for external installs.** Add root-aware scanner helpers or a `SourceProfileScope` model: `listHermesProfilesAtRoot(root)`, `profileHomeAtRoot(root, profile)`, `readMemoryAtHome(home)`, `listSkillsAtHome(home)`, `listSessionMetadataAtHome(home)`, `listCronJobsAtHome(home)`, and `readConfigSummaryAtHome(home)`.
3. **Build Hermes explicit-profile inventory first.** Produce high-confidence candidate cards from default/named profile homes, using metadata-first summaries: model/provider, `.env` presence, `auth.json` presence/provider labels, SOUL/memory existence and safe summaries, skill names/descriptions, cron counts, session counts/date ranges/source/model, and collisions.
4. **Centralize migration privacy/redaction before deep summaries.** Treat `.env`, `auth.json`, `credentials/`, `auth-profiles.json`, tokens/passwords/API keys, channel/account IDs, phone numbers, emails, raw sessions, logs, prompt text, and transcript-derived titles/snippets as privacy-classed artifacts. Default UI should show existence/counts/mtimes/date ranges/hashes, not raw values.
5. **Build OpenClaw inventory as a separate scanner.** Validate research-backed roots and layouts with fixtures or real installs. Scan `~/.openclaw`, legacy roots, `~/.openclaw-*`, env/config overrides, configured agents, workspace persona/memory files, `agents/<agentId>/sessions`, jsonl transcripts, cron/task ledgers, skill roots, channel/account bindings, and credentials presence. Do not rely on `hermes claw migrate --preset full` for preview.
6. **Add synthesized candidate discovery after explicit candidates work.** Cluster sessions by metadata/topic/source/date/profile, cron jobs by prompt/skills/delivery, skills by bundle/category/scripts, memory/persona files by themes/headings, and channel/platform traces by redacted identities. Mark synthesized candidates as recommendations with confidence and evidence, not automatic imports.
7. **Separate inventory/plan/apply APIs.** Add read-only APIs such as `inventoryMigrationSources`, `planHermesAgentInventory`, and `planOpenClawAgentInventory`; keep apply as a later explicit step such as `applyMigrationPlan(selection)`. Apply must handle backups, collisions, secret opt-in, runtime stale marking, and session-cache resync.
8. **Wire contracts through service, IPC, preload, CLI, and docs/tests.** Add service methods in a migration service or install service, IPC/preload types, `docs/contracts/ipc-preload.md`, CLI read-only commands such as `mercury migration inventory` / `mercury openclaw inventory`, and parity tests in `tests/ipc-handlers.test.ts`, `tests/preload-api-surface.test.ts`, `tests/cli-parity.test.ts`, and CLI command tests.
9. **Design the UI as a candidate picker, not a migrate button.** Replace the coarse migration banner with an inventory/results flow: source roots, candidate cards, confidence, evidence paths, privacy flags, selected target profile, collisions, and explicit apply choices.

## Preventive Measures
- Keep inventory read-only and side-effect-free; runtime/cache invalidation belongs only to apply.
- Treat user-facing migration claims as contract-backed: only promise artifact categories that scanners can inventory and tests cover.
- Never show secrets or raw transcript/log/prompt content by default; require explicit consent for deep content summarization or migration of secrets.
- Maintain fixtures for old Hermes roots, OpenClaw roots, alternate env/config roots, sparse installs, and legacy layouts.
- Add tests that prove default inventory output is redacted, root-parameterized, non-mutating, and stable enough for a user-pickable candidate list.
