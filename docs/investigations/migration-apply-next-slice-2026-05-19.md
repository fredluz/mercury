# Investigation: Migration Apply Next Slice

## Summary
The next slice should be a local-only Hermes migration plan/apply path built on the existing redacted inventory scanner. It should let users select explicit inventory candidate IDs, map them to target Mercury profiles, preview collisions/deferred artifacts, and apply only safe Hermes artifacts (`SOUL.md`, `memories/MEMORY.md`, `memories/USER.md`, Markdown-only skills) with file-level backups and runtime-stale marking. OpenClaw remains preview-only/deferred for apply in this slice.

## Symptoms
- Inventory now produces user-pickable candidate agents, but there is no apply/import path for selected candidates.
- The next slice needs to convert selected inventory candidates into a concrete migration plan with target profile mapping, collision handling, backup requirements, and privacy/secret opt-ins.
- We need enough structure that an implementation agent can build it safely without mutating real external installs or collapsing inventory and apply into one risky operation.

## Background / Prior Research
- Prior inventory report: `docs/investigations/migration-agent-inventory-2026-05-19.md` recommends read-only inventory, redaction-first candidate cards, explicit user selection, and later plan/apply APIs.
- Prior migration report: `docs/investigations/migration-hermes-openclaw-2026-05-19.md` found Mercury has profile-aware Hermes archive import and a coarse OpenClaw shell-out, but no first-class Mercury-owned migration planner/apply domain.
- Implemented first slice now includes shared migration inventory types, a redacted scanner in `src/main/migration/inventory.ts`, CLI commands under `migration/hermes/openclaw inventory`, IPC channel `migration-inventory`, and preload `getMigrationInventory`.

### Phase 2 - Next Slice Verification (2026-05-19)

#### Verdict
- **Recommended slice:** build a local-only `MigrationPlan` / `MigrationApply` path, but keep it deliberately small: shared contracts, read-only plan from selected inventory candidate IDs plus explicit target profiles, and apply only deterministic safe artifacts after source re-resolution and backups.
- **Important refinement:** the shared `CandidateAgent` inventory output is a **redacted presentation contract**, not an apply manifest. Apply must not copy from `CandidateEvidence.path`; it must internally re-resolve artifacts from trusted source roots/options and selected candidate IDs.
- **OpenClaw should be preview-only in this slice.** Current OpenClaw inventory is useful for candidate cards, but OpenClaw’s agent/workspace layouts do not map 1:1 to Mercury profiles, and the existing executable migration is a coarse upstream shell-out (`hermes claw migrate --preset full`) without Mercury-owned artifact-by-artifact apply control.

#### 1. Shared types: current `CandidateAgent` is enough for selection, not for apply
- Current shared migration types stop at inventory. `src/shared/migration.ts` defines `MigrationSourceKind`, `CandidateAgentOrigin`, `PrivacyFlag`, `InventoryArtifactKind`, `CandidateEvidence`, `CandidateActivity`, `CandidateAgent`, `MigrationInventorySource`, `MigrationInventoryOptions`, and `MigrationInventory`, with no plan/apply DTOs (`src/shared/migration.ts:1-91`).
- `CandidateAgent` has enough UI/CLI selection metadata: stable-ish `id`, `sourceKind`, `origin`, `displayName`, `sourceRoots`, `sourceProfiles`, `evidence`, summaries, activity, privacy flags, proposed target profile, and warnings (`src/shared/migration.ts:41-60`). That supports a plan request like `{ inventoryOptions, selections: [{ candidateId, targetProfile, artifactKinds }] }`.
- It is **not** enough as an apply manifest. Evidence paths are generated through `pathLabel(root, path)` and `sanitizePathLabel`, which intentionally produce relative/redacted labels (`src/main/migration/inventory.ts:105-108`, `src/main/migration/inventory.ts:134-148`). Sensitive path components can be replaced with `redacted-<hash>` (`src/main/migration/inventory.ts:119-125`).
- Inventory also redacts raw content: Hermes SOUL/MEMORY/USER evidence reports presence only and carries `raw-content-redacted` / `pii-redacted` flags (`src/main/migration/inventory.ts:202-222`); tests assert that secrets, private soul text, memories, prompts, and OpenClaw transcripts do not serialize (`tests/migration-inventory.test.ts:22-70`, `tests/migration-inventory.test.ts:72-109`).
- Candidate IDs are derived from hashes of internal source homes/dirs (`hermes-profile:${hash(home)}:${targetProfile}` and `openclaw-agent:${hash(agentDir)}:${targetProfile}`), but those hashes are not reversible into filesystem paths (`src/main/migration/inventory.ts:328-345`, `src/main/migration/inventory.ts:576-603`). Plan/apply can use IDs to reselect candidates after rescanning; it should not try to reconstruct paths from IDs.

#### 2. Main-process plan/apply module design and source resolution
- Add shared contracts in `src/shared/migration.ts` rather than ad-hoc payloads. Suggested minimum:
  - `MigrationArtifactKind` / reuse `InventoryArtifactKind`, but add apply-specific statuses: `planned`, `skipped`, `unsupported`, `conflict`, `applied`, `failed`.
  - `MigrationPlanRequest`: normalized inventory options, selected candidate IDs, explicit `targetProfile` per candidate, optional artifact-kind allowlist, collision policy defaulting to `skip`.
  - `MigrationPlan`: generated time, selected candidates, redacted source/destination labels, artifact actions, conflicts, backup requirement, unsupported/deferred items, privacy warnings, and a deterministic `planFingerprint`.
  - `MigrationApplyRequest`: same selection/options plus accepted `planFingerprint` and explicit confirmation flags; apply recomputes the plan and refuses if the fingerprint changed.
  - `MigrationApplyResult`: per-artifact results, backup path(s), affected profiles, runtime/cache follow-up warnings.
- Put source resolution in new main-process code such as `src/main/migration/plan.ts` and `src/main/migration/apply.ts`, or a combined `src/main/migration/apply-plan.ts`. Keep the existing `src/main/migration/inventory.ts` as the redacted scanner, but add internal resolver helpers that return non-exported `ResolvedMigrationCandidate` / `ResolvedMigrationArtifact` records with absolute source paths.
- Resolution rule: **re-run inventory from normalized options, match selected candidate IDs, then derive artifacts from source roots/profile homes with code paths, not from redacted evidence labels.** For Hermes, derive default home from selected root and named profile homes from `<root>/profiles/<name>`; current scanner already enumerates default plus named profile dirs (`src/main/migration/inventory.ts:362-391`).
- For Hermes source artifacts, resolve only deterministic files/dirs already scanned: `SOUL.md`, `memories/MEMORY.md`, `memories/USER.md`, and `skills/<category>/<skill>/SKILL.md`. The scanner’s current Hermes memory and skill evidence paths come from those exact locations (`src/main/migration/inventory.ts:202-222`, `src/main/migration/inventory.ts:224-251`).
- For OpenClaw, plan can display inferred artifacts from persona/memory and skills evidence (`src/main/migration/inventory.ts:431-456`, `src/main/migration/inventory.ts:462-471`, `src/main/migration/inventory.ts:535-548`), but apply should report them as `unsupported`/`previewOnly` until a separate OpenClaw resolver fixture suite proves exact source-to-target mapping.
- Do not wire this through remote/SSH connection behavior in this slice. Existing profile writes often branch on `getConnectionConfig()` for SSH/remote in services, but migration apply should be local-only and should fail closed if connection mode is pure remote or if target profile paths cannot be resolved locally (`src/main/services/knowledge-service.ts:47-217`, `src/main/services/config-service.ts:79-127`).

#### 3. Reusable safe write/import/stale primitives, and their limits
- Destination profile mapping already exists: `profileHome(profile?)` maps `default`/undefined to `HERMES_HOME` and named profiles to `HERMES_HOME/profiles/<name>` (`src/main/utils.ts:22-26`). Reuse that for target paths.
- `safeWriteFile` creates parent directories and writes UTF-8 content (`src/main/utils.ts:40-44`). It is useful as a baseline, but it is **not atomic** and does not back up old files. Migration apply should wrap it with target backup + temp-file/rename or at least pre-copy backups before overwrite.
- SOUL writes already use `safeWriteFile` via `writeSoul(content, profile?)` (`src/main/soul.ts:23-31`). This can be reused if the collision policy says overwrite or target is empty.
- Memory helpers are profile-aware but have UI/runtime limits: `addMemoryEntry` rejects files over 2,200 chars and `writeUserProfile` rejects USER content over 1,375 chars (`src/main/memory.ts:5-6`, `src/main/memory.ts:132-153`, `src/main/memory.ts:192-205`). For migration preservation, a raw artifact copy helper may be better than these UI-edit helpers; if reusing them, the plan must surface `would-exceed-limit` conflicts.
- Markdown skill import is the best existing reusable import primitive: `prepareSkillMarkdownImport` validates markdown size, NUL bytes, slug name/category, and normalizes frontmatter (`src/main/skills/importer.ts:7-18`, `src/main/skills/importer.ts:78-151`). `importSkillMarkdown` validates profile slug, resolves under `<profileHome>/skills`, checks path escape, detects duplicates unless `overwrite`, writes `SKILL.md`, and returns a typed duplicate/write-failed result (`src/main/skills/importer.ts:153-211`). It only imports the Markdown file, which matches this slice’s “Markdown skills only” scope.
- Service-level stale marking is already centralized for knowledge mutations: `markProfileMutation` calls `markRuntimeStale(profile, '<area> changed for profile runtime.')` (`src/main/services/knowledge-service.ts:43-45`), and SOUL/user/memory/skills mutations call it on success (`src/main/services/knowledge-service.ts:57-91`, `src/main/services/knowledge-service.ts:99-113`, `src/main/services/knowledge-service.ts:180-217`). Migration apply should similarly mark every affected target profile stale once after successful writes.
- Runtime stale semantics are explicit: `markRuntimeStale` sets `staleReason`, `staleAt`, and `apiServerAvailable=false`; revalidation only clears stale after verified profile identity (`src/main/hermes/runtime/manager.ts:304-350`). The gateway barrel exposes `markRuntimeStale`, `markAllRuntimesStale`, `clearRuntimeStale`, and `revalidateRuntime` (`src/main/hermes/gateway.ts:101-122`).

#### 4. Service, IPC/preload, CLI, docs, and tests to add
- Prefer a dedicated service (`src/main/services/migration-service.ts`) or a clearly separated migration section in `install-service`. Current inventory lives in `install-service` with input normalization caps of 8 roots and 4096 chars per root (`src/main/services/install-service.ts:24-25`, `src/main/services/install-service.ts:135-163`). Reuse/extend those normalization rules for plan/apply and add candidate/target profile validation.
- IPC should add kebab-case channels such as `migration-plan` and `migration-apply`. Existing handler registration is in `src/main/ipc/index.ts`, which wires each module’s `register*Ipc` function (`src/main/ipc/index.ts:1-24`). Either extend `src/main/ipc/install.ts` next to `migration-inventory` or create `src/main/ipc/migration.ts` and register it.
- Preload must be updated in three places: add methods in a preload fragment (currently `getMigrationInventory` is in `src/preload/api/install.ts:67-70`), ensure `hermesAPI` spreads that fragment (`src/preload/api/index.ts:9-16`), and update `HermesAPI` types in `src/preload/index.d.ts` where migration currently only exposes inventory/check/run (`src/preload/index.d.ts:79-86`).
- Contract tests enforce symmetry. `tests/ipc-handlers.test.ts` requires every preload invoke to have a matching `ipcMain.handle` and vice versa (`tests/ipc-handlers.test.ts:104-112`), and `tests/preload-api-surface.test.ts` requires quoted kebab-case channels (`tests/preload-api-surface.test.ts:343-360`). Add plan/apply channels to the new-feature handler list and migration preload assertions (`tests/ipc-handlers.test.ts:141-164`, `tests/preload-api-surface.test.ts:154-159`).
- CLI convention: `migration plan` belongs in read-only dispatch next to `migration inventory` (`src/cli/read-only-commands.ts:271-304`, `src/cli/read-only-commands.ts:317-343`). `migration apply` belongs in mutating dispatch with `ensureResultSuccess` and optional NDJSON progress, following the existing install/update/claw progress pattern (`src/cli/mutating-commands.ts:153-163`, `src/cli/mutating-commands.ts:507-537`, `src/cli/mutating-commands.ts:559-583`).
- CLI entrypoint already reserves `migration` and `openclaw` domains (`src/cli/index.ts:33-66`) and dispatches chat → read-only → mutating before placeholder errors (`src/cli/index.ts:212-231`). Add tests in `tests/cli-read-only-commands.test.ts` for `migration plan` and `tests/cli-mutating-commands.test.ts` for `migration apply`, using temp `HERMES_HOME` fixtures like existing inventory and mutation tests (`tests/cli-read-only-commands.test.ts:143-168`, `tests/cli-mutating-commands.test.ts:52-105`).
- Docs must move with the contract. IPC/preload change rules require preload implementation, `HermesAPI` type, main handler, CLI parity decision, tests, and docs together (`docs/contracts/ipc-preload.md:178-193`). Update `docs/contracts/cli.md` where migration/openclaw inventory is currently documented as read-only and `claw migrate` as the coarse OpenClaw path (`docs/contracts/cli.md:1393-1395`).
- Add behavior tests beyond surface tests: `tests/migration-plan.test.ts` for selected IDs, target profile mapping, conflicts, deferred artifacts, and redaction; `tests/migration-apply.test.ts` for backups, collision policies, safe writes, stale marking, and “do not trust evidence.path” by including redacted/sensitive source names.

#### 5. Backup, collision, runtime, and cache constraints
- Require a backup before destructive writes. Existing `runHermesBackup(profile?)` shells to `hermes backup [-p profile]` and extracts a backup path from output (`src/main/install/maintenance.ts:7-42`). It is useful when Hermes is installed, but migration apply should also have a file-level backup fallback for individual target artifacts because `safeWriteFile` itself has no backup/atomicity (`src/main/utils.ts:40-44`).
- Default collision policy should be `skip` or `rename`, never silent overwrite. Plan should detect existing target `SOUL.md`, `memories/MEMORY.md`, `memories/USER.md`, and `skills/<category>/<name>/SKILL.md`; `importSkillMarkdown` already reports duplicate skills unless `overwrite` is true (`src/main/skills/importer.ts:184-190`).
- Normalize and validate target profile names before writing. Skill import already accepts only `default` or slug-like names (`src/main/skills/importer.ts:11-18`, `src/main/skills/importer.ts:153-161`); plan/apply should use at least that strictness instead of the looser runtime `normalizeProfile`, which only trims/defaults (`src/main/hermes/runtime/profile.ts:3-7`).
- Mark affected runtimes stale after successful apply. For per-profile writes, use `markRuntimeStale(targetProfile, 'Migration apply changed profile runtime files.')`; for a multi-profile apply, mark each affected profile, not all profiles unless the plan touched shared/global files. This mirrors Hermes import’s stale behavior (`src/main/services/system-service.ts:31-37`).
- Do not perform session-cache work in this slice if sessions/state DB imports are deferred. Session cache sync reads profile DBs and writes global desktop cache (`src/main/session-cache.ts:283-326`); since raw sessions are explicitly deferred, applying SOUL/memory/USER/Markdown skills should not need cache resync.
- Config/model/env cache invalidation is out of scope because config writes and secrets are deferred. Current config cache invalidation only happens inside config setters (`src/main/config.ts:94-98`, `src/main/config.ts:150-153`, `src/main/config.ts:270-273`), so raw migration writes must either use setters or explicitly invalidate if config/env become future scope.

#### 6. OpenClaw preview-only rationale
- Current OpenClaw execution is not safe enough for this small apply slice: `runClawMigrate` requires Hermes, detects a fixed OpenClaw home, and spawns `[HERMES_SCRIPT, 'claw', 'migrate', '--preset', 'full']` with no source, target profile, dry-run, conflict, or secret controls surfaced (`src/main/install/executor.ts:12-49`).
- Current detection only checks `~/.openclaw`, `~/.clawdbot`, and `~/.moldbot` (`src/main/install/paths.ts:284-293`), while the inventory scanner already considers more roots including `.openclaw-*`, `OPENCLAW_STATE_DIR`, and `OPENCLAW_CONFIG_PATH` (`src/main/migration/inventory.ts:645-664`). That mismatch means “apply” would not necessarily act on the same source the user previewed.
- OpenClaw evidence is inferred from persona files, sessions JSON/jsonl, auth profiles, credentials dirs, root/workspace skills, task ledger, and cron (`src/main/migration/inventory.ts:431-456`, `src/main/migration/inventory.ts:473-603`). Those are good preview signals but not yet a Mercury-owned apply mapping.
- Therefore this slice should show OpenClaw candidates and planned safe-artifact possibilities as preview/deferred items, but should not write OpenClaw-derived artifacts. A later OpenClaw apply slice needs fixture-backed resolver tests, source-root parity with inventory, explicit target-profile mapping, credential policy, and replacement of or deliberate wrapping around upstream `claw migrate` controls.

#### Recommended implementation batches
1. **Contracts + normalization:** extend `src/shared/migration.ts` with `MigrationPlan*` and `MigrationApply*` DTOs; add service input normalization for roots, candidate IDs, target profiles, artifact allowlists, collision policy, and local-only mode.
2. **Planner:** add main-process planner that rescans inventory, matches selected IDs, resolves internal source artifacts, emits redacted plan actions, target paths/labels, conflicts, backup requirement, and deferred unsupported categories. Include explicit “do not use evidence.path for source copy” tests.
3. **Safe Hermes apply:** implement local-only apply for Hermes profile candidates and safe artifacts only: `SOUL.md`, `memories/MEMORY.md`, `memories/USER.md`, and Markdown-only skills. Back up target files, skip/rename/overwrite by explicit policy, use skill Markdown importer where possible, and mark affected profiles stale.
4. **Surfaces:** wire `migration-plan` / `migration-apply` through service, IPC, preload/types, CLI (`migration plan`, `migration apply`), and contract docs/tests.
5. **Hardening tests:** add fixture tests for collisions, backups, stale marking, redacted path labels, duplicate skills, invalid profiles, oversized memory/user files, remote-mode failure, and OpenClaw preview-only/deferred results.

#### Explicitly eliminated or deferred from this slice
- Deferred: secrets and credentials (`.env`, `auth.json`, OpenClaw `auth-profiles.json`, `credentials/`).
- Deferred: raw sessions/transcripts, `state.db`, `sessions/*.jsonl`, session-cache sync, logs, prompt text, cron jobs, channels, config/model writes, desktop connection config, MCP config, plugin/script/reference skill bundles, and full OpenClaw migration.
- Eliminated for implementation: using `CandidateEvidence.path` as a copy source. It is a redacted label by design, not a trusted filesystem path.
- Eliminated for this slice: invoking `runClawMigrateForConnection` as “apply”; it is a coarse upstream full migration wrapper and does not share inventory source/target/collision semantics (`src/main/services/install-service.ts:166-176`).

## Root Cause
The first migration slice created a redacted inventory contract, but inventory candidates are presentation records, not apply manifests. `CandidateEvidence.path` is intentionally a sanitized/redacted label, and candidate IDs select candidates only after a fresh scan; neither can safely be used as a source filesystem path. The missing next layer is a main-process planner/resolver that re-runs inventory from normalized source roots, matches explicit user-selected candidate IDs, internally resolves concrete source artifacts, previews target collisions, and applies only allowlisted artifacts to Mercury-owned profile homes.

The apply boundary also needs to respect current Mercury storage semantics. `profileHome(profile)` maps target profiles to profile homes; `safeWriteFile`, `importSkillMarkdown`, and runtime stale helpers are reusable, but memory UI helpers impose size/semantic limits and should not be used for raw `MEMORY.md` / `USER.md` preservation. The legacy OpenClaw migration path is still a coarse upstream shell-out and does not share inventory source/root/collision semantics, so it should not be treated as the apply implementation for this slice.

3. **Batch 3 — Safe Hermes apply.** Add local-only apply for Hermes profile candidates only. Apply `SOUL.md`, `memories/MEMORY.md`, `memories/USER.md`, and Markdown-only skills. Never mutate source roots, never copy secrets/sessions/logs/cron/config, create file-level backups before overwrite, support `skip`/`rename`/`overwrite`, and mark each affected profile stale exactly once.
4. **Batch 4 — Surfaces.** Wire `migration-plan` and `migration-apply` through service, IPC, preload/types, CLI, and docs. `migration plan` is read-only; `migration apply --plan-file <path> --yes` is mutating and consumes an auditable plan file.
5. **Batch 5 — Tests.** Add planner/apply tests for explicit selection, invalid profiles, redacted output, evidence-path non-use, collision policies, source immutability, file-level backups, stale marking, local-only failure, OpenClaw deferred operations, and no secret/session/transcript migration. Update IPC/preload/CLI/docs parity tests.
6. **Batch 6 — UI later.** Only after contracts/services/CLI are proven, replace the Settings banner flow with candidate selection, target profile mapping, plan preview, and apply result UI. Keep legacy `runClawMigrate` separate/advanced, not the primary apply path.

## Preventive Measures
- Add regression tests that fail if plan/apply ever uses `CandidateEvidence.path` as a source path.
- Keep source roots read-only and test source-file hashes before/after apply.
- Keep all secret/transcript/prompt flags false by default and treat unsupported artifacts as plan-visible but non-applyable.
- Require explicit user selection and target profile mapping; never apply “all candidates” implicitly.
- Require a successful backup path or file-level backup before overwrite.
- Mark only affected profiles stale; do not use broad stale invalidation unless a future global/shared artifact migration actually touches global state.
- Keep OpenClaw apply behind a separate future fixture-backed resolver design because inventory roots and legacy upstream migration roots do not currently match.
